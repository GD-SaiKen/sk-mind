## 1. 同步触发机制

### 1.1 三种触发方式

| 触发方式 | 入口 | 适用场景 | 实现 |
|---|---|---|---|
| **手动触发** | 管理台按钮 | 首次全量同步、问题修复后重试、临时补数据 | 前端 POST → 后端创建批次 → RQ 入队 |
| **定时触发** | APScheduler / cron | 日常增量同步（T+1 凌晨） | 定时器 → 后端创建批次 → RQ 入队 |
| **条件触发** | Agent / 事件 | Agent 请求实时数据、Schema 变化告警后自动复检 | 内部服务调用 → 创建轻量批次 → 不入常规队列 |

### 1.2 手动触发流程

```text
┌──────────┐    POST /api/v1/ingestion-tasks/{id}/execute    ┌──────────┐
│ 管理台     │ ──────────────────────────────────────────────→ │ FastAPI   │
│ 点击"执行" │                                                │ 后端      │
└──────────┘                                                └────┬─────┘
                                                               │
                                                    ① 校验任务状态（非 running）
                                                    ② 生成 batch_id
                                                    ③ 写入 IngestionBatch (pending)
                                                    ④ enqueue RQ Job
                                                    ⑤ 返回 batch_id + job_id
                                                               │
                                                               ▼
┌──────────┐    RQ Queue "ingestion"                   ┌──────────┐
│ Worker   │ ←───────────────────────────────────────── │ Redis    │
│ 拉取 Job │                                            │ 队列     │
└────┬─────┘                                           └──────────┘
     │
     │ ⑥ 更新批次状态 → running
     │ ⑦ 执行同步（全量/增量/API 拉取）
     │ ⑧ 实时更新 job.meta.progress
     │ ⑨ 完成后更新批次 → success / partial_success / failed
     │
     ▼
┌──────────┐
│ PostgreSQL│
│ 批次记录  │
│ 错误明细  │
│ Raw 数据  │
│ 血缘记录  │
└──────────┘
```

### 1.3 定时触发实现

```python
# app/core/scheduler.py

from apscheduler.schedulers.background import BackgroundScheduler
from app.modules.ingestion.services.task_service import TaskService

scheduler = BackgroundScheduler()

def setup_scheduled_tasks():
    """注册定时同步任务"""
    # 每日凌晨 2:00 — ERP 主数据增量同步
    scheduler.add_job(
        trigger_erp_incremental_sync,
        trigger="cron",
        hour=2, minute=0,
        id="erp_incremental_daily",
    )
    # 每日凌晨 3:00 — ERP 交易表增量同步
    scheduler.add_job(
        trigger_erp_transaction_sync,
        trigger="cron",
        hour=3, minute=0,
        id="erp_transaction_daily",
    )
    # 每小时 — MES 三色灯状态拉取（实时性要求高）
    scheduler.add_job(
        trigger_mes_trilight_sync,
        trigger="interval",
        minutes=60,
        id="mes_trilight_hourly",
    )


def trigger_erp_incremental_sync():
    """定时触发 ERP 增量同步"""
    db = SessionLocal()
    try:
        service = TaskService(db)
        # 查找所有启用定时调度的 ERP 增量任务
        tasks = service.find_tasks_by_type("incremental_sync", source_type="erp")
        for task in tasks:
            batch_id = service.trigger_execution(task.id, trigger_type="scheduled")
            logger.info("定时同步已触发: task=%s, batch=%s", task.name, batch_id)
    finally:
        db.close()
```

### 1.4 状态流转

```text
                    ┌─────────┐
                    │  draft  │  任务草稿，未启用
                    └────┬────┘
                         │ 用户启用任务
                         ▼
                    ┌─────────┐
          ┌────────→│ pending │←────────┐
          │         └────┬────┘         │
          │              │ 触发执行      │ 重试
          │              ▼              │
          │         ┌─────────┐         │
          │         │ running │         │
          │         └────┬────┘         │
          │              │              │
          │     ┌────────┼────────┐     │
          │     ▼        ▼        ▼     │
          │ ┌───────┐┌──────────┐┌────┐│
          │ │success││ partial  ││fail││
          │ └───────┘│_success  │└───┬┘│
          │          └────┬─────┘    │ │
          │               │          │ │
          │               └──────────┘ │
          │                           │
          └───────────────────────────┘
              手动重试 → 创建新批次
```

- `draft → pending`：任务配置完成，首次启用
- `pending → running`：Worker 开始执行
- `running → success`：全部成功
- `running → partial_success`：部分行失败（如 10000 行中 12 行格式错误）
- `running → failed`：连接失败、认证失败等全局错误
- 重试 = 创建**新批次**，旧批次记录保留不变

### 1.5 进度上报

Worker 执行过程中通过 RQ 的 `job.meta` 上报进度：

```python
# 管理台轮询 GET /api/v1/ingestion-batches/{batch_id}/progress
# 返回 { "progress": 65, "step": "同步中 65000/100000", "status": "running" }

def _update_progress(self, rq_job, progress: int, step: str):
    """每分钟至少更新一次进度"""
    if rq_job:
        rq_job.meta["progress"] = progress
        rq_job.meta["step"] = step
        rq_job.save_meta()
```

### 2.1 API 端点总览

### 2.2 关键交互流程

#### 2.2.1 手动执行 + 进度轮询

```typescript
// 前端 — 手动触发表单提交
async function handleExecute(taskId: number) {
  // 1. 触发执行
  const { batchId } = await executeTask(taskId);   // POST /tasks/{id}/execute

  // 2. 开始轮询进度（每 2 秒）
  const timer = setInterval(async () => {
    const progress = await getBatchProgress(batchId);  // GET /batches/{id}/progress
    updateProgressBar(progress.percent);
    updateStepText(progress.step);

    if (progress.status !== 'running') {
      clearInterval(timer);
      showResult(progress.status);                      // 显示成功/失败
      reloadBatchList();
    }
  }, 2000);
}
```

#### 2.2.2 错误清单加载

```typescript
// 前端 — 批次详情 → 错误明细 Tab
async function loadErrors(batchId: string, page: number) {
  const res = await getBatchErrors(batchId, { page, pageSize: 20 });
  // res.data.items: [{ errorLevel, errorType, errorLocation, errorMessage, sampleData }]
  // res.data.total: 45  // 总错误数
  renderErrorTable(res.data.items);
}
```

#### 2.2.3 重试

```typescript
// 前端 — 点击"重试"
async function handleRetry(batchId: string) {
  await ElMessageBox.confirm('将基于该批次的配置创建新的同步任务，是否继续？');
  const { newBatchId } = await retryBatch(batchId);  // POST /batches/{id}/retry
  ElMessage.success(`重试任务已创建，批次号: ${newBatchId}`);
  startPolling(newBatchId);
}
```

## 4. 失败处理与重试

### 4.1 错误分类

| 错误级别 | 含义 | 处理方式 | 影响 |
|---|---|---|---|
| **系统级** | 连接失败、认证失败、OOM | 任务立即停止，标记 `failed` | 整个批次 |
| **对象级** | 某张表/某个接口完全无法访问 | 跳过该对象，继续处理其他 | 该对象的数据不更新 |
| **行级** | 单行格式错误、类型转换失败、必填缺失 | 跳过该行，记录错误，继续处理 | 该行数据不入库 |
| **字段级** | 某个字段值异常但行仍可入库 | 标记质量警告，行正常入库 | 该字段标记为异常 |

### 4.2 重试决策树

```text
批次状态 = failed / partial_success
│
├── 错误类型 = 系统级（连接/认证）
│   └── 需人工介入（检查网络、凭据、源系统状态）→ 修复后手动重试
│
├── 错误类型 = 行级（格式/类型/缺失）
│   ├── 错误行数 < 总行数 × 1%
│   │   └── 可接受（partial_success），不自动重试，用户可选择重试失败行
│   └── 错误行数 > 总行数 × 10%
│       └── 告警 → 人工检查源数据质量 → 修正后手动重试
│
└── 错误类型 = 对象级（表/接口不可用）
    └── 检查源对象状态 → 修复后手动重试
```

### 4.3 手动重试流程

```text
用户点击"重试"
→ 弹出确认框：将创建新的同步批次，旧批次记录保留
→ 用户确认
→ POST /api/v1/ingestion-batches/{batchId}/retry
→ 后端：
   ① 读取旧批次的 task_id 和 source_object_id
   ② 生成新 batch_id
   ③ 创建新 IngestionBatch (pending, trigger_type=retry)
   ④ 入队 RQ Job
   ⑤ 返回新 batch_id
→ 前端跳转到新批次进度页面
```

**自动重试规则**：

- 系统级错误**不自动重试**（连接失败重试无意义，需人工介入）
- 行级错误**不自动重试**（数据问题不会因重试而修复）
- 仅 API 限流（429）和临时网络错误由 Connector 内部自动重试（已在 §03 定义）

### 4.4 部分成功处理

部分成功 (`partial_success`) 是最常见的状态，设计要点：

- **已成功的数据正常入库**，可通过 Raw 层查询
- **失败行记录在 `import_error` 表**，含错误位置、原因、原始数据
- **后续增量同步不受影响**：增量以时间戳/hash 判断，不依赖上次是否全量成功
- **Clean 层对 `partial_success` 的数据做质量标记**，标注哪些行未经过完整校验

## 5. 日志体系

### 5.1 日志分层

### 6.1 PostgreSQL 物理布局

```text
PostgreSQL 实例 :5432
└── skmind（数据库）
    │
    ├── platform schema          — 平台元数据 (~50 表)
    │   ├── data_source            数据源登记
    │   ├── source_object          来源对象（表/接口定义）
    │   ├── connector_config       连接配置（加密存储）
    │   ├── ingestion_task         同步任务配置
    │   ├── ingestion_batch        执行批次记录
    │   ├── import_error           错误明细
    │   ├── data_lineage           数据血缘
    │   ├── audit_log              审计日志
    │   └── ...
    │
    ├── raw schema               — 原始数据层
    │   ├── erp_dbo_SALE_ORDER       ERP 物理表（字段 = 源表 + 追踪字段）
    │   ├── erp_dbo_INVENTORY
    │   ├── erp_dbo_CUSTOMER
    │   ├── ...                      (~2000 张 ERP 表, 按需创建)
    │   └── api_record               API JSONB 通用表
    │       ├── _raw_id              BIGSERIAL PK
    │       ├── _batch_id            VARCHAR(64)
    │       ├── _source_system       VARCHAR(64)  -- 'MES_LIGHT' / 'SRM'
    │       ├── _source_object       VARCHAR(256) -- 接口端点
    │       ├── _source_row_hash     VARCHAR(64)  -- SHA-256
    │       ├── _api_url             VARCHAR(512)
    │       ├── _api_request_params  JSONB
    │       ├── _api_response_at     TIMESTAMPTZ
    │       ├── _ingested_at         TIMESTAMPTZ
    │       ├── _is_deleted          BOOLEAN
    │       └── payload              JSONB        -- 原始响应
    │
    ├── clean schema             — 清洗数据层
    │   ├── erp_dbo_SALE_ORDER       清洗后的 ERP 表
    │   │   ... (源表字段 + _quality_status + _clean_batch_id)
    │   ├── mes_workorder            从 api_record.payload 展开的结构化表
    │   └── srm_supplier             从 api_record.payload 展开的结构化表
    │
    └── serving schema           — 服务视图层
        ├── v_sales_order            业务视图（JOIN 多表）
        ├── v_inventory_summary      库存汇总视图
        ├── v_production_progress    生产进度视图
        └── mv_daily_kpi             物化视图（每日 KPI）
```

### 6.2 Raw → Clean → Serving 流转

```text
┌─────────────────────────────────────────────────────────┐
│ Raw 层                                                   │
│ - ERP 源表 1:1 物理映射                                   │
│ - API 响应 JSONB 完整保留                                 │
│ - 无业务清洗，仅追加追踪字段                               │
│ - 批次可重放                                              │
└──────────────────────┬──────────────────────────────────┘
                       │ CleanTask（RQ Worker）
                       ▼
┌─────────────────────────────────────────────────────────┐
│ Clean 层                                                 │
│ - 类型转换（SQL Server → PG 类型）                        │
│ - 日期/金额/编码格式标准化                                │
│ - 去重（基于 _source_row_hash）                           │
│ - 质量标记（_quality_status: ok/warning/error）            │
│ - API JSONB → 结构化字段展开                              │
└──────────────────────┬──────────────────────────────────┘
                       │ ServingTask（RQ Worker / 手动触发）
                       ▼
┌─────────────────────────────────────────────────────────┐
│ Serving 层                                               │
│ - CREATE VIEW v_sales_order AS SELECT ... FROM clean...   │
│ - 业务语义合并（订单头 JOIN 订单行 JOIN 客户）             │
│ - 物化视图（高频查询场景）                                 │
│ - 权限控制（视图级 GRANT）                                │
│ - Agent 工具入口（所有 Agent 查询必须走 Serving 层）       │
└─────────────────────────────────────────────────────────┘
```

### 6.3 数据保留策略

| 数据层 | 保留策略 | 清理方式 |
|---|---|---|
| Raw 层 | 永久保留（可溯源） | 按批次归档到冷存储（后续版本） |
| Clean 层 | 保留最新 3 个版本 | 旧版本标记 `_is_archived = true` |
| Serving 层 | 视图（无存储开销）/ 物化视图（定时刷新） | 视图直接指向 Clean 表最新数据 |
| 错误明细 | 保留 90 天 | 定时 DELETE |
| 批次记录 | 永久保留 | 不删除 |

### 6.4 备份策略

```text
# 每日全量备份
pg_dump -U postgres -d skmind \
  --schema=platform \
  --schema=raw \
  --schema=clean \
  --schema=serving \
  | gzip > /backup/skmind_$(date +%Y%m%d).sql.gz

# 保留最近 7 天 + 每月 1 号的归档
# Raw 层数据量大时可单独备份策略：
#   platform schema: 每次备份（元数据不可丢）
#   raw schema: 每周备份（可从源重放，备份优先级低）
```

## 7. 同步任务生命周期总览

```text
┌──────────────────────────────────────────────────────────────┐
│                        任务生命周期                           │
│                                                              │
│  ① 创建任务                                                  │
│     管理台填写任务名、选数据源、选表/接口、配调度 → 保存       │
│     status = draft                                            │
│                                                              │
│  ② 启用任务                                                  │
│     管理台点击"启用" → status = pending                       │
│     定时调度开始生效（如配置了 cron）                          │
│                                                              │
│  ③ 触发执行                                                  │
│     ├── 手动: 管理台点击"执行" → POST /tasks/{id}/execute     │
│     └── 定时: APScheduler → 内部调用 trigger_execution()      │
│     → 生成 batch_id → IngestionBatch(pending) → RQ 入队       │
│                                                              │
│  ④ Worker 执行                                               │
│     RQ Worker 拉取 Job → 更新 batch 为 running                │
│     ├── 连接数据源（数据库/API）                               │
│     ├── 分页拉取数据                                          │
│     ├── 逐行/逐批写入 Raw 层                                   │
│     ├── 实时更新进度 (job.meta)                                │
│     └── 记录错误明细 (import_error)                            │
│                                                              │
│  ⑤ 执行结果                                                  │
│     ├── success → 更新 last_sync_time → 触发 Clean 任务       │
│     ├── partial_success → 标记哪些行失败 → 用户可选择重试      │
│     └── failed → 记录失败原因 → 发送通知 → 等待人工介入        │
│                                                              │
│  ⑥ 后续处理（自动触发）                                       │
│     成功 → CleanTask 入队 → 清洗数据 → ServingTask 入队       │
│     → 更新数据目录 → 更新血缘记录 → Agent 可查询新数据         │
│                                                              │
│  ⑦ 停用/删除                                                 │
│     管理台点击"停用" → status = disabled → 定时调度停止        │
│     管理台点击"删除" → 软删除 → 历史批次记录保留               │
└──────────────────────────────────────────────────────────────┘
```
