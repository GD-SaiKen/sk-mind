## 一、首页

> 参考：原型说明 §5

### 页面目标

📋 让平台管理员和数据负责人快速了解平台运行状态，发现异常并进入处理页面。

### 页面布局

```
首页
┌──────────────────────────────────────────────────┐
│ 状态总览卡片（5 个，一行排列）                     │
├─────────────────────┬────────────────────────────┤
│ 待处理事项           │ 最近接入任务（Top 5）        │
├─────────────────────┴────────────────────────────┤
│ 快捷入口                                          │
└──────────────────────────────────────────────────┘
```

> 📋 原型原设计包含独立的「数据质量概览」和「Agent 使用概览」区块，但 §5.2 原文自注它们与状态卡片"有点重复"。💡 合并到对应的状态卡片中，不单独出区块。

### 状态总览卡片

> 📋 5 个核心指标卡片，点击卡片跳转对应列表页并自动带上筛选条件。

| 卡片 | 展示内容 | 点击跳转 | 说明 |
|---|---|---|---|
| 数据源 | 总数 / 正常 / 异常 | 数据源列表（筛选：正常+异常） | 📋 |
| 接入任务 | 成功 / 失败 / 部分成功（近 24 小时） | 接入任务列表（筛选：失败） | 📋 |
| 数据表 | 总数 / 已开放给 Agent | 数据表列表（筛选：Agent 可用） | 📋 |
| 数据质量 | 通过 / 警告 / 异常 | 数据质量 → 问题清单 | 📋 合入了原本独立的"数据质量概览"区块 |
| 语义模型 | 对象数 / 映射数 | 语义模型 → 业务对象列表 | 📋 原型第 6 个卡片为空，💡 推断此处为 Agent 使用概览合入后的指标：Agent 查询次数（今日）/ 失败次数 |

> 📋 原型补充说明：第 6 个卡片内容为空（`└─` 之后无内容）。四个候选：
> - Agent 使用数据（查询次数/失败次数）——原型在"Agent 使用概览"中提到，合入卡片
> - 语义映射统计（待确认映射数）——也是语义模型模块的核心指标
>
> 💡 **当前选择：语义模型（对象数/映射数）作为第 5 个卡片。** 语义模型是整个链路的关键中间层，合入卡片区更合理。Agent 使用数据放在待处理事项旁的另一个卡片或直接看"最近接入任务"下方的趋势。

### 待处理事项

> 📋 聚合各模块待人工处理的事项，展示数量 Badge，点击跳转对应处理页面。

| 事项 | 数量来自 | 点击跳转 |
|---|---|---|
| 接入失败任务 | 接入任务列表（状态=失败） | 接入任务列表（筛选：失败） |
| 待确认字段说明 | 字段列表（字段说明为空） | 数据表详情 → 字段列表 |
| 待确认质量问题 | 问题清单（状态=未处理/处理中） | 数据质量 → 问题清单 |
| 待确认关系边 | 关系图谱（确认状态=待确认） | 关系图谱 → 待确认关系 |

> 📋 原型还列出了"Excel 解析失败文件"，但 💡 这个已经在"接入任务失败"中通过批次错误清单体现，不需要重复列出。如果错误清单中 Excel 解析失败占比高，可以在接入失败任务旁边加一个 `Excel 解析失败：N 个文件` 的子行。

### 最近接入任务

> 📋 展示最近 5 次任务执行情况，只看关键信息。

| 展示内容 | 说明 |
|---|---|
| 任务名称 | 点击跳转任务详情 |
| 数据源 | 📋 |
| 执行时间 | 📋 |
| 状态 + 摘要 | 📋 成功："同步 12,450 行" / 失败："连接超时" / 部分成功："成功 180 行，失败 3 行" |

> 点击行 → 跳转批次详情。点击"查看全部"→ 跳转接入任务列表。

### 快捷入口

> 📋 5 个高频操作入口。

| 入口 | 跳转 | 说明 |
|---|---|---|
| 新增数据源 | 数据源新增 | 📋 |
| 创建接入任务 | 接入任务创建 | 📋 |
| 查看数据目录 | 数据目录 | 📋 |
| 执行质量检查 | 数据质量 → 执行记录 → 一键触发最近规则 | 📋。💡 点击后弹窗确认"将对所有启用的质量规则执行一次检查"，确认后自动跳转执行记录页 |
| 进入 Agent 查询 | Agent 查询入口 | 📋 |

### 关键交互

- 📋 点击状态卡片 → 对应列表页，自动带上筛选条件
- 📋 点击待处理事项 → 问题详情或任务详情
- 📋 首页不做复杂趋势分析，只做基础状态概览

### 页面验收标准

- ✅ 📋 可以看到数据源、接入、质量、语义和 Agent 的基础状态
- ✅ 📋 异常事项可从首页进入处理
- ✅ 📋 首页指标与各模块列表数据一致

**案例一：正常运行的数据库直连**

```
数据源名称   ERP-赛肯生产库      ← 拿什么数据：ERP系统的生产库
类型         ERP                ← 从什么渠道：ERP系统
接入方式     数据库同步           ← 怎么搬运：直连数据库同步
状态         🟢 正常             ← 最近一次接入成功，数据可用
业务负责人   李工                ← 数据含义/业务影响，找ta
技术负责人   黄工                ← 连接/配置/执行问题，找ta
标签         核心系统、生产相关    ← 业务分类：属于核心系统，涉及生产业务
最近接入时间 2026-07-14          ← 数据新鲜度，最后一次跑的时间
关联任务数   3                  ← 挂了几个接入任务，点数字可跳转
操作         查看 | 编辑 | 创建任务 | 停用
```

> 这是最典型的状态。一切正常，数据持续更新，业务和技术负责人分工明确。

**案例二：异常状态的 API 拉取**

```
数据源名称   MES-制造执行         ← 拿什么数据：制造执行系统数据
类型         MES                ← 从什么渠道：MES系统
接入方式     API 拉取            ← 怎么搬运：调用API接口
状态         🟡 异常             ← 最近一次接入失败，需要关注
业务负责人   王工                ← 先找ta确认：数据还要不要？影响范围多大？
技术负责人   张工                ← 排查接口问题的人
标签         核心系统、生产相关    ← 与案例一同属核心系统和生产板块，标签一致

**案例三：已停用的文件导入**

```
数据源名称   考勤-Excel导入       ← 拿什么数据：考勤系统导出的Excel
类型        Excel               ← 从什么渠道：只知道是Excel文件，说不出具体系统名
接入方式    文件导入              ← 怎么搬运：上传文件
状态        ⚫ 停用              ← 管理员手动关闭，不再接入新数据

### 数据源核心概念辨析

> 经过梳理讨论，对数据源三个核心字段的最终理解如下。

#### 三个字段各回答一个问题

```
数据源名称："EPR-生产订单"        ← 拿什么数据
类型："ERP"                  ← 从什么渠道
接入方式："数据库同步"         ← 用什么技术手段

一句话：从 ERP 系统，通过数据库同步，拿生产订单数据。
```

三个字段各司其职，拼接起来就是把一件事说清楚。名称是用户自由填的标签，类型是 9 选 1 的枚举，接入方式决定技术层面的搬运策略。

#### 关于"数据源系统"的概念

真实世界中存在上游业务软件（如 SAP ERP、黑湖 MES、钉钉考勤），一个系统可能通过多种方式提供数据：

```
SAP ERP（真实系统，不在平台内）
├─ 数据源："ERP-生产订单库"   类型=ERP   接入方式=数据库同步
├─ 数据源："ERP-销售报表"     类型=ERP   接入方式=Excel 导入
└─ 数据源："ERP-物料主数据"   类型=ERP   接入方式=API 拉取
```

> **注意**：原型中**没有"数据源系统"这个实体**。上述三个数据源"同属 SAP ERP"这件事只存在于创建者的认知中，系统不做约束——类型各填各的，没有任何字段将它们归组。基础阶段数据源数量有限，这样简化是合理的。后续如果出现"同一系统挂了多个数据源、每次重复填信息"的痛点，再考虑引入"系统"实体。

#### 关于"类型"枚举值混合的问题

原型"类型"的 9 个可选值（ERP / MES / 采购 / 考勤 / 数据库 / API / Excel / 共享盘 / 其他）混合了两个维度——业务系统分类和技术交付形态。这是由于缺少"系统"实体导致的简化处理，在基础阶段可以接受。**核心逻辑通顺，不需要改动**。使用策略：知道是 ERP 就选 ERP，只知道连了数据库就选数据库，只知道有人发 Excel 就选 Excel——选最贴切的即可。

### 状态与操作联动 💡

> 原型 §6.4 列出了 5 种状态及页面表现，但**没有明确描述操作按钮如何随状态变化**。下表是基于原型各状态描述做的推断：

| 状态 | 含义 | 页面表现 | 💡 推断的操作按钮 |
|---|---|---|---|
| 未接入 | 📋 还没创建过接入任务 | 📋 提示创建接入任务 | 查看 / 编辑 / 创建任务 / 停用 |
| 接入中 | 📋 有任务正在执行 | 📋 展示运行中的任务 | 查看 / 编辑 / 创建任务 |
| 正常 | 📋 最近一次接入成功 | 📋 展示最近成功时间 | 查看 / 编辑 / 创建任务 / 停用 |
| 异常 | 📋 最近一次接入失败 | 📋 展示失败原因和负责人 | 查看 / 编辑 / 创建任务 / 停用 / 重试 |
| 停用 | 📋 管理员手动关闭 | 📋 隐藏高风险操作，仅保留查看 | 查看 / 编辑 / 启用 |

> ❓ **待确认**："接入中"状态是否应该隐藏停用按钮（不能停掉正在跑的任务）？

### 标签

#### 它解决什么问题

用"类型"筛选只能按数据从什么渠道来分类。但实际工作中常需要跨类型看数据：

```
假设你有这些数据源：

ERP-生产订单库      类型=ERP      数据库同步
MES-制造执行        类型=MES      API 拉取
采购-供应商主数据    类型=采购     数据库同步
ERP-财务月报        类型=ERP      Excel 导入
考勤-打卡记录       类型=Excel    文件导入
```

类型能做和不能做的事：

| 场景             | 用类型能解决吗                                       |
| -------------- | --------------------------------------------- |
| "有哪些 ERP 数据源？" | ✅ 筛 类型=ERP → 2 条                              |
| "哪些属于核心系统？"    | ❌ ERP 的两个 + MES + 采购都在核心系统之列，但分散在三个类型里，类型筛不出来 |
| "哪些还在试点阶段？"    | ❌ 考勤打卡是试点，但它的类型是 Excel，和"试点"没有关系              |
| "哪些涉及财务？"      | ❌ ERP-财务月报涉及，ERP-生产订单不涉及，但类型都是 ERP，无法区分       |

标签就是来解决这些"类型做不到"的场景的。

#### 它是什么

标签是一组**用户自定义的业务标记**，给数据源打上跨类型的分类。

给上面的数据源打上标签之后：

```
ERP-生产订单库      类型=ERP     标签：核心系统、生产相关
MES-制造执行        类型=MES     标签：核心系统、生产相关
采购-供应商主数据    类型=采购     标签：核心系统
ERP-财务月报        类型=ERP     标签：核心系统、财务相关
考勤-打卡记录       类型=Excel   标签：试点项目
```

现在筛选就灵活了：

| 想看什么 | 怎么筛 | 结果 |
|---|---|---|
| 所有核心系统 | 标签=核心系统 | 4 条（跨 ERP、MES、采购三个类型） |
| 所有生产相关 | 标签=生产相关 | 2 条（ERP 生产 + MES） |
| 试点项目 | 标签=试点项目 | 1 条（考勤打卡） |
| 核心 + 生产 | 标签=核心系统 AND 生产相关 | 2 条 |

#### 标签 vs 类型

两个字段各回答一个完全不同的问题：

| | 类型 | 标签 |
|---|---|---|
| 回答什么 | "数据从什么渠道来" | "这个数据源对公司有多重要、属于哪个业务板块" |
| 谁定义 | 系统固定枚举，9 选 1 | 用户自己维护字典，想加什么加什么 |
| 几个 | 一个数据源只能有一个 | 一个数据源可以打多个 |
| 例子 | ERP、MES、Excel | 核心系统、试点项目、财务相关、生产相关、已归档 |

**类型和标签各管各的，互不取代。** 类型是渠道视角，标签是业务视角。

### 新增数据源

> 原型 §6.2 写为"分步 5 步"，§4.3 提到复杂操作可采用向导式流程。

#### 表单形式分析 💡

原型原文用了"分步"一词，但实际看这 5 步的内容：

| 步骤 | 内容 | 操作量 |
|---|---|---|
| 1 | 填基本信息 | 数据源名称、所属系统、类型、备注，4 个字段 |
| 2 | 定接入方式 | 下拉 5 选 1 |
| 3 | 配负责人和标签 | 选两个人 + 打标签 |
| 4 | 保存并点下一步 | 两个按钮 |

每一步都很轻，如果做成每页点一下「下一步」的 5 页向导，体验反而比一页表单差——用户会觉得"这么简单为什么翻 5 页"。

**结论：用单页分区表单，不用分步向导。**

```
新增数据源

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、基本信息
  数据源名称：[___]           ← 必填，建议只描述数据内容，如"生产订单数据"，不包含系统名
  所属系统：[___]             ← 选填，自由文本。上游业务系统名称，如"SAP ERP"、"黑湖MES"
  类型：[下拉] ERP / MES / 采购 / 考勤 / 数据库 / API / Excel / 共享盘 / 其他
  备注：[___]                ← 选填，为什么要建、有什么注意事项

二、接入配置
  接入方式：[下拉] 数据库直连 / API / Excel 导入 / 共享盘扫描

三、负责人与标签
  业务负责人：[___]  技术负责人：[___]
  标签：[___]（字典建成前自由文本输入）⏸️
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[保存]  [保存并创建接入任务]
```

三个分区的逻辑：说清楚这是什么（名称 + 来源 + 类型 + 备注）→ 决定怎么搬（接入方式）→ 指定谁负责（负责人 + 标签）。底部两个按钮对应原型步骤 5 的两种保存行为——「保存」只存数据源，「保存并创建接入任务」存完后跳到创建接入任务页。

> 💡 真正需要用分步向导的场景是 **Excel 批量导入配置、语义映射** 等复杂操作。数据源新增不属于这类。

#### 详情页主操作 💡

> 原型 §6.3 列出四个主操作按钮：编辑 / 创建任务 / 检测连接 / 停用。但**没有说明按钮和状态的联动关系**。下表是基于各状态含义做的推断：

| 按钮   | 作用          | 何时出现                               |
| ---- | ----------- | ---------------------------------- |
| 编辑   | 修改数据源配置     | 所有状态（停用除外 ❓）                       |
| 创建任务 | 跳转到创建接入任务页  | 未接入、接入中、正常、异常 → 都需要新建任务的能力         |
| 检测连接 | 连通性验证：能连上且能正常响应，不验证数据内容。按接入方式区分具体行为（见下方说明） | 正常、异常 → 排查连接问题时用；未接入 → 数据源还没配好，没必要测；停用 → 已关闭，不显示 |

#### 检测连接的按接入方式区分 💡

| 接入方式 | 具体行为 | 示例 |
|---|---|---|
| 数据库同步 | 尝试连接 + 执行 `SELECT 1`，确认能登录且能查询 | 连 MySQL：`mysql -h host -u user -p -e "SELECT 1"` |
| API 拉取 | 发一个最小请求（如健康检查端点），确认返回 200 | `GET /health` → 200 OK |
| 共享盘扫描 | 检查目录路径是否存在、是否可读 | `ls /mnt/shared/erp_data/` |
| 文件导入 / Excel 导入 | 不适用，提示"文件类数据源无需检测连接" | 弹 toast："文件导入方式无需检测连接" |

> 一句话：验证**能不能连上**，不验证**数据对不对**。数据内容是否正确由接入任务执行时校验。
| 停用   | 手动关闭数据源     | 未接入、接入中、正常、异常 → 需要停用的场景            |
| 启用   | 重新激活已停用的数据源 | 仅停用状态，替换「停用」按钮出现                   |
| 重试   | 重新执行失败的接入   | 仅异常状态                              |

按状态汇总：

| 状态  | 详情页操作按钮                           |
| --- | --------------------------------- |
| 未接入 | 📋 编辑 / 创建任务 / 停用                 |
| 接入中 | 编辑 / 创建任务 / 停用（检测连接和重试不需要——正在跑着呢） |
| 正常  | 编辑 / 创建任务 / 检测连接 / 停用             |
| 异常  | 编辑 / 创建任务 / 检测连接 / 停用 / 重试        |
| 停用  | 📋 编辑 / 启用（停用不影响配置修改——改备注、换负责人、调标签完全合理。创建任务和检测连接隐藏——不接入新数据也没必要测连通性） |

#### 其他标签页

| 标签页 | 内容 | 实现状态 |
|---|---|---|
| 接入任务 | 📋 关联的接入任务列表 | ⬜ |

#### 层级流转 💡

> 数据写入后自动从 Raw 到 Clean 再到 Serving，用户不手动操作层级。

| 层级 | 阶段 | 触发条件 |
|---|---|---|
| **Raw** | 原始层 | 接入任务执行成功时自动创建。数据保持源系统形态，未做清洗 |
| **→ Clean** | 清洗层 | Raw 层数据通过清洗规则后自动升级。❓ 触发条件可能：标准化清洗（去重、格式化、空值处理）通过？还是人工确认？ |
| **→ Serving** | 服务层 | Clean 层数据标记为对外可用。❓ 触发条件可能：Clean 层数据稳定 + 字段说明已补充 + 敏感字段已标记？ |

> ❓ **待确认**：每层升级的具体触发条件（自动规则？人工确认？定时触发？）。

#### Agent 可用 💡

> 不是创建后默认全开的人工开关。平台自动检查，检查结果决定可用状态。

```
数据表创建
  → 平台自动检查：
    ① 质量规则是否通过？
    ② 敏感字段是否已标记？
    ③ 字段说明是否已补充？
  → 全部通过 → 自动标为「Agent 可用」
  → 有未通过项 → 标记「不可用」，附带具体原因（如"质量未通过"/"存在未标记的敏感字段"）
```

管理员可在详情页手动覆盖此标记（强制开启或关闭），但默认值由检查结果决定。

> ❓ **待确认**：检查项是否有遗漏？Agent 是否需要按类型分类授权（查询类/分析类/写操作类各自有不同可用状态）？

## 核心流程串联

> 参考：原型说明 §16

### 主流程

```
数据源列表 → 新增数据源 → 创建接入任务 → 任务详情 → 批次详情
→ 数据表详情 → 字段说明维护 → 数据目录详情 → 权限配置
→ Agent 可用标识 → Agent 查询入口
```

### 四个核心子流程

1. **Excel 批量导入**：数据源 → 接入任务 → 上传模板 → 字段确认 → 批量执行 → 批次/错误清单 → 产出数据表
2. **语义映射到图谱**：数据表 → 字段 → 业务对象 → 属性 → DataMapping → SemanticRelation → BusinessGraphEdge
3. **数据质量到 Agent 提示**：数据表 → 质量检查 → 问题清单 → 质量状态 → Agent 回答引用
4. **数据同步** 💡（非原型内容，自行补充）：中间服务器 → 同步脚本 → 数据校验（隔离区）→ Raw 层写入 → 水位更新

### 流程串联的关键"衔接点" 💡

| 衔接 | 从哪里 | 到哪里 | 靠什么串联 |
|---|---|---|---|
| 源→任务 | 数据源详情「创建接入任务」按钮 | 创建任务页 | `数据源.id` → `任务.数据源_id` |
| 任务→表 | 任务详情「产出数据表」标签页 | 数据表详情 | `任务.批次.id` → `数据表.来源批次` |
| 表→目录 | 数据表字段维护（补充说明、标记敏感）→ 数据目录自动同步展示 | 数据集详情 | 表与数据集是同一数据的双视图 |
| 表→质量 | 数据表详情「质量结果」标签页 | 数据集质量详情 | `数据表.id` → `质量检查.数据集_id` |
| 质量→权限 | 数据集质量达标 → 开放权限配置 | 数据集权限页 | `数据集.id` → `数据集权限.数据集_id` |
| 权限→语义 | 字段已标记敏感 → 映射到语义属性时标注敏感等级 | 数据映射页 | `字段.id` → `数据映射.来源字段` + `对象属性.敏感等级` |
| 语义→图谱 | 定义 SemanticRelation → 系统生成 BusinessGraphEdge | 关系边列表 | `语义关系` → `关系边.relation_name` + `关系边.from/to_entity` |
| 图谱→Agent | Agent 做关系查询时调用图谱查询工具 | Agent 回答 | `Agent工具.图谱查询` → `BusinessGraphEdge` 路径 |
| 全链路→Agent | Agent 查询汇总所有模块能力 | Agent 回答引用区 | 数据目录检索 + 权限检查 + 质量状态 + 语义检索 + 受控查询 + 图谱查询 |
