# 08-同步引擎优化方案（d2a 对标）

> **背景**：MES API 同步引擎已跑通安灯 + OEE 两个报表，核心链路（水位增量 + 3天回放 + upsert 幂等 + row_hash 跳过）稳定。对标技术顾问的 d2a 整 ERP 数据库同步方案后，识别出 6 个值得对齐的缺口。本方案给出每个缺口的具体实现设计。

## 一、缺口总览与优先级

| # | 缺口 | 优先级 | 风险 | 预计改动量 |
|---|---|---|---|---|
| 1 | 对账机制缺失 | P0 | 数据静默丢失 | 中（1新模块 + 1新表） |
| 2 | Schema 漂移容错 | P0 | 新字段静默丢弃 | 小（改2方法） |
| 3 | 隔离区 + 熔断器 | P1 | 坏数据不可追溯 | 中（1新表 + 改验证逻辑） |
| 4 | 定时调度 | P1 | 无自动同步 | 中（1新模块 + 启动脚本） |
| 5 | 软删除检测 | P2 | ERP数据删除无感知 | 中（1新列 + 1新模块） |
| 6 | 声明式映射层 | P3 | 无 raw→clean 转换 | 大（后续独立方案） |

> **建议实施顺序**：1 → 2 → 4 → 3 → 5 → 6。前两个堵数据丢失风险，第四个是上生产刚需，后三个看业务需要。

## 二、对账机制（P0）

### 2.1 问题

增量只回放"水位往前 3 天"的窗口，MES 后来回填的历史日期（如 OEE 的 simDate 在 2025-09~2026-07 之间被补录）永远漏拉。当前只能靠手动全量重载兜底，没有自动发现机制。

### 2.2 设计：三级对账

借鉴 d2a 的 E3 分段对账，但适配 API 场景（不能直接 COUNT 源表）。

#### L1 — 轻量对账（每次增量后自动执行）

**原理**：`HttpxApiConnector.fetch_page()` 已经从 `total_path` 提取了 `total`（如 `totalItems`），但 `fetch_all_pages()` 只 yield records，把 total 丢了。捕获这个 total，和 DB 行数对比。

**流程**：
- 取 API 第一页返回的 `total`（记为 `api_total`）
- **对比基准按同步模式分作用域**（关键，否则会出现负差异率 / 掩盖丢数）：
  - **全量同步**：`compared = db_count`（`SELECT COUNT(*) FROM raw.{table}`，raw 表按接口分表，无需 `_source_id` 过滤）
  - **增量同步**：`compared = pulled_count`（**本批实际翻页拉取行数**），**不查整表**——增量窗口的 `api_total` 只是近期总量，与历史累计的整表行数量纲不同，相减会得到负差异率（如 -5000%）且无业务含义；更严重的是 `diff = api_total - 整表` 恒为负，`diff<=0→pass` 会**掩盖窗口内真实丢数**
- 差异 = `api_total - compared`
- `compared == api_total` → `pass`；`compared < api_total`（窗口内未拉全，可能分页截断 / API 丢返回）→ 记录对账告警，差异率 > 阈值（如 5%）→ 自动触发 L2

**状态分级规则**（三份文档统一）：

| 差异率 | status | 含义 | 前端颜色 |
|---|---|---|---|
| `diff_count == 0` | `pass` | 完全一致 | 绿色 |
| `0 < diff_ratio < threshold` | `warning` | 有差异但未超阈值 | 黄色 |
| `diff_ratio >= threshold` | `failed` | 差异超阈值 | 红色 |
| L2 修复后 | `repaired` | 已修复 | 蓝色（info） |

> `threshold` 来自 YAML `reconciliation.threshold_pct`（默认 5）。前端差异列颜色也使用此阈值动态判断，不写死。

> **⚠️ 前置验证（必须先做）**：在实现 L1 对账前，**必须先验证 MES API 的 `total` 是否随日期参数变化**。验证方法：用不同日期范围调接口，看 `total` 是否不同。
> - 如果 `total` 受日期参数过滤 → 与**本批拉取数 `pulled_count`** 对比合理（注意**不是**整表行数），L1 在增量后执行
> - 如果 `total` 不受过滤（返回全量总数）→ 与增量拉取数对比**仍不公平**，会频繁误报；此时 L1 只能在**全量同步后**执行，增量后跳过
> - **实现决策（2026-07-25 修正）**：即便 `total` 受过滤、增量 L1 可执行，对比基准也必须用 `pulled_count`（本批实际翻页拉取行数），而非整表 `COUNT(*)`。原实现用整表行数对比窗口 `api_total`，实测产生 -5000% 负差异率，且 `diff<=0→pass` 掩盖了窗口内真实丢数。同步模式由引擎在调用 `reconcile_l1()` 时传入 `sync_mode` 与 `pulled`。

**改动点**：

| 文件 | 改动 |
|---|---|
| `connectors/api_client.py` | `fetch_all_pages` 返回 `(records_iterator, first_page_total)` 或新增 `fetch_total()` 方法 |
| `engines/api_sync_engine.py` | `_sync_interface` 末尾调 `Reconciler.reconcile_l1()` |
| **新建** `ingestion/reconciler.py` | `Reconciler` 类：`reconcile_l1()`、`reconcile_l2()` |

#### L2 — 深度对账（定时触发，如每天凌晨）

**原理**：用宽日期范围拉一次全量（不带水位过滤），按日期分段对比行数。

**流程**：
1. 按 `time_config` 的日期字段分段（如按天）
2. 每段：API 拉取该日期范围的 total vs DB 该日期范围的 COUNT
3. 不一致的段 → 标记为"需修复"
4. 修复方式：对该日期范围重新全量拉取 + upsert

**改动点**：

| 文件 | 改动 |
|---|---|
| `ingestion/reconciler.py` | `reconcile_l2()` 方法：分段拉取 + 逐段对比 + 触发修复 |
| `tasks/sync_tasks.py` | 新增 `run_reconciliation` RQ 任务入口 |

#### L3 — 行级对账（可选，按需触发）

**原理**：对 PK-based 接口，拉取全量 PK 列表，和 DB PK 对比，找出缺失的行。

> L3 成本较高（需拉全量 PK），仅在前两级发现差异后手动触发，或作为定期（如每周）深度检查。

## 三、Schema 漂移容错（P0）

### 3.1 问题

`_ensure_raw_table` 只在首次建表时按 API 返回推断列。MES 后续给接口加新字段时，`ColumnMapper` 会静默丢弃（`api_mapper.py` 第 44 行：`scalar not in table columns → silently drop`）。

### 3.2 设计：自动加列

**流程**：
1. 在 `_sync_interface()` 中，`_ensure_raw_table()` 调用之后、`ColumnMapper` 初始化之前，调用 `_check_schema_drift()`
2. 对比 `sample_row`（实际返回的第一行数据）的 keys 和 DB 现有列
3. 新增的 key → `ALTER TABLE raw.{table} ADD COLUMN "{col}" TEXT`
4. 记录 schema 变更事件到审计表
5. 更新 ColumnMapper 的列集合

> **注意**：不能放在 `_ensure_raw_table()` 内部，因为该方法在表已存在时直接 `return`，不会执行后续代码。漂移检测必须放在 `_sync_interface()` 中独立调用，每次同步都执行。

**改动点**：

| 文件 | 改动 |
|---|---|
| `engines/api_sync_engine.py` | `_sync_interface()` 中 `_ensure_raw_table()` 之后调用 `_check_schema_drift()`；新增 `_check_schema_drift(target_table, sample_row)` 方法 |
| `connectors/api_mapper.py` | 无需改（列集合来自 DB 查询，ALTER 后自动包含） |

### 3.3 新方法

```python
# api_sync_engine.py 新增
def _check_schema_drift(self, target_table: str, sample_row: dict) -> list[str]:
    """检测并处理 schema 漂移：API 返回了新字段但 DB 表没有对应列。

    Returns: 新增的列名列表（空列表 = 无漂移）
    """
    existing = self._get_table_business_columns(target_table)
    sample_cols = {ColumnMapper._to_snake(k) for k in sample_row.keys()}
    new_cols = sample_cols - existing

    if not new_cols:
        return []

    schema, table = target_table.split(".", 1)
    for col in sorted(new_cols):
        self._db.execute(text(
            f'ALTER TABLE {target_table} ADD COLUMN IF NOT EXISTS "{col}" TEXT'
        ))
        logger.warning("Schema drift: %s 新增列 %s", target_table, col)

    self._db.commit()

    # 记录审计
    self._db.execute(text(
        "INSERT INTO sync_schema_changes (table_name, change_type, column_name, detail) "
        "VALUES (:t, 'added', :c, :d)"
    ), {"t": target_table, "c": ",".join(sorted(new_cols)),
        "d": json.dumps({"sample_keys": list(sample_row.keys())})})
    self._db.commit()

    return sorted(new_cols)
```

## 四、定时调度（P1）

### 4.1 问题

当前只能手动触发同步（前端点按钮 → RQ 入队）。`IngestionTask` 表已有 `schedule_type`（manual/cron/on_demand）和 `cron_expression` 字段，但没有调度器读取它们。

### 4.2 设计：APScheduler 集成

**架构**：

```
┌─────────────────┐     ┌──────────────┐     ┌──────────┐
│  APScheduler    │────▶│  RQ Queue    │────▶│  Worker  │
│ (定时触发器)     │     │  (ingestion) │     │ (执行同步)│
└─────────────────┘     └──────────────┘     └──────────┘
```

调度器只负责"到点入队"，实际执行仍走 RQ Worker。这样不会阻塞调度器，也不会和正在跑的同步冲突。

**改动点**：

| 文件 | 改动 |
|---|---|
| **新建** `backend/app/modules/ingestion/scheduler.py` | `SyncScheduler` 类：APScheduler 实例管理、任务注册、动态增删 |
| **新建** `backend/run_scheduler.py` | 启动脚本（与 `run_worker.py`/`run_api.py` 同级，`backend/` 根目录，git 跟踪） |
| `models.py` | 无需改（字段已有） |
| `router.py` | 任务创建/更新/删除时**写 DB 即可**，调度器通过 DB 轮询自动感知（见下方联动机制） |

#### 调度器与 API 进程的跨进程联动

> **问题**：APScheduler 使用 `MemoryJobStore`，运行在 `run_scheduler.py` 独立进程中。router 在 API 进程中，两者不共享内存。router 中直接调 `scheduler.register()` 无法影响 scheduler 进程。

**方案（推荐）：DB 轮询**
- scheduler 每 60 秒扫描 `IngestionTask` 表，对比 DB 中的 active cron 任务和内存 jobstore 中的 job
- 新增/修改/删除的任务自动同步到 jobstore（`add_job(replace_existing=True)` / `remove_job(if_exists)`）
- 优点：简单可靠，无需额外通信组件
- 缺点：最多 60 秒延迟（对同步任务完全可接受）

```python
# scheduler.py 中新增
def _sync_from_db(self):
    """定期从 DB 重新加载 cron 任务，与内存 jobstore 对齐。"""
    db_tasks = self._db.execute(text(
        "SELECT id, cron_expression FROM ingestion_tasks "
        "WHERE schedule_type='cron' AND status='active'"
    )).fetchall()
    db_ids = {str(row.id) for row in db_tasks}
    db_job_ids = {f"sync_task_{sid}" for sid in db_ids}  # 提到循环外，避免重复构建

    # 注册新增/修改的
    for row in db_tasks:
        job_id = f"sync_task_{row.id}"
        try:
            trigger = CronTrigger.from_crontab(row.cron_expression)
            self._scheduler.add_job(
                func=self._enqueue_sync, trigger=trigger, args=[str(row.id)],
                id=job_id, replace_existing=True,
            )
        except Exception as e:
            logger.error("注册调度任务失败 %s: %s", job_id, e)

    # 注销已删除/禁用的
    for job in self._scheduler.get_jobs():
        if job.id.startswith("sync_task_") and job.id not in db_job_ids:
            self._scheduler.remove_job(job.id)

def start(self):
    """启动调度器，从 DB 加载任务，并启动 DB 轮询。"""
    self._sync_from_db()
    # 每 60 秒从 DB 重新同步
    self._scheduler.add_job(
        func=self._sync_from_db, trigger="interval", seconds=60, id="db_sync"
    )
    self._scheduler.start()
```

### 4.3 核心实现

```python
# ingestion/scheduler.py
from apscheduler.schedulers.blocking import BlockingScheduler
from apscheduler.triggers.cron import CronTrigger
from apscheduler.jobstores.memory import MemoryJobStore

class SyncScheduler:
    """定时调度器：到点把同步任务入 RQ 队列。

    设计要点：
    - max_instances=1, coalesce=True：同一任务不重叠、不错过
    - 调度器只入队，不执行：实际同步走 RQ Worker
    - 内存 jobstore：重启后从 DB 重新加载（不持久化 job 状态）
    - DB 轮询（60秒）：独立进程，通过定期扫描 DB 感知任务变更，无需跨进程通信
    """

    def __init__(self):
        self._scheduler = BlockingScheduler(
            jobstores={"default": MemoryJobStore()},
            job_defaults={"max_instances": 1, "coalesce": True},
        )

    def start(self):
        """启动调度器，从 DB 加载所有 cron 任务，并启动 DB 轮询同步。"""
        self._sync_from_db()
        # 每 60 秒从 DB 重新同步（检测新增/修改/删除的 cron 任务）
        self._scheduler.add_job(
            func=self._sync_from_db, trigger="interval", seconds=60, id="db_sync"
        )
        self._scheduler.start()

    def _sync_from_db(self):
        """从 IngestionTask 表加载 schedule_type='cron' 的任务，与内存 jobstore 对齐。"""
        # SELECT id, cron_expression FROM ingestion_tasks
        # WHERE schedule_type='cron' AND status='active'
        # 注册新增/修改的，注销已删除/禁用的
        ...

    def register(self, task_id: str, cron_expr: str):
        """注册一个定时同步任务（也可被 _sync_from_db 间接调用）。"""
        trigger = CronTrigger.from_crontab(cron_expr)  # 5段式：分 时 日 月 周
```

## 五、隔离区 + 熔断器（P1）

### 5.1 问题

`_validate_rows` 丢弃 PK 为空 / 批内重复的行后，这些行就没了——不可追溯、不可重试。接 ERP 业务数据时（不像 MES 报表那么干净），坏数据会更多。

### 5.2 设计

#### 隔离区表

```sql
CREATE TABLE sync_quarantine (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    batch_id        UUID NOT NULL,
    data_source_id  UUID NOT NULL,

    pk_value        TEXT,                    -- 拒绝时的 PK 值（可能为空）
    rejection_reason VARCHAR(100) NOT NULL,  -- null_pk / dup_in_batch / type_error / write_error
    raw_json        JSONB NOT NULL,          -- 原始 API 行数据
    status          VARCHAR(20) NOT NULL DEFAULT 'pending',  -- pending / retried / resolved / ignored
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    retried_at      TIMESTAMPTZ,
    resolved_at     TIMESTAMPTZ
);
CREATE INDEX idx_quarantine_batch ON sync_quarantine(batch_id);
CREATE INDEX idx_quarantine_status ON sync_quarantine(status);
```

| 文件 | 改动 |

#### 熔断器

```python
# _sync_interface 末尾
quarantine_rate = rejected / pulled if pulled > 0 else 0
threshold = self._get_config("quarantine_threshold_pct", 5)  # 从 YAML 读取，默认 5%
if quarantine_rate > threshold / 100:
    logger.warning("隔离率 %.1f%% 超阈值 %.0f%%，触发熔断告警", quarantine_rate * 100, threshold)
    # 写告警到 sync_reconciliations 或单独的 alerts 表
    # 不中断同步（已写入的数据是好的），但标记批次为 partial_success
```

> **注意**：熔断器阈值从 YAML 配置读取（`quarantine.threshold_pct`，默认 5），不要写死。对账/隔离区/Schema 漂移等新增逻辑均需 `try/except` 保护，避免异常中断同步主流程。

#### 数据清理策略

审计表（`sync_reconciliations`/`sync_schema_changes`/`sync_quarantine`）会随运行时间无限增长，需定期清理：

| 表 | 保留策略 | 清理方式 |
|---|---|---|
| `sync_reconciliations` | 保留最近 90 天 | 定时任务 `DELETE WHERE checked_at < now() - interval '90 days'` |
| `sync_schema_changes` | 全部保留（变更频率低） | 不清理 |
| `sync_quarantine` | 已解决（`status='resolved'`/`'ignored'`）的保留 30 天后清理 | 定时任务 `DELETE WHERE status IN ('resolved','ignored') AND created_at < now() - interval '30 days'` |

## 六、软删除检测（P2）

### 6.1 问题

MES 报表数据一般只增不删，影响不大。但后续接 ERP 业务数据（订单作废、物料删除）时，源端删除的行在 DB 中不会被标记，导致数据"永远存在"。

### 6.2 设计

**原理**：对 PK-based 接口，定期拉取全量 PK 列表，DB 中有但 API 没有的 PK → 标记为软删除。

**流程**：
1. 分页拉取该接口的全量数据（仅 PK 字段，或用专用 PK 列表接口），每页 5000 条
2. 将 API PK 写入临时表 `tmp_api_pks_{table}`（`CREATE TEMP TABLE ... AS`）
3. DB 中该表的 PK 集合
4. 用 `NOT EXISTS` 找出差集并标记（只更新 `_deleted_at IS NULL` 的行，避免重复更新）：

```sql
-- 单字段 PK
UPDATE raw.{table} t
SET _deleted_at = now()
WHERE t._deleted_at IS NULL
  AND NOT EXISTS (
    SELECT 1 FROM tmp_api_pks_{table} p WHERE p.pk = t.{pk_col}
  );

-- 多字段 PK（组合主键）
UPDATE raw.{table} t
SET _deleted_at = now()
WHERE t._deleted_at IS NULL
  AND NOT EXISTS (
    SELECT 1 FROM tmp_api_pks_{table} p
    WHERE p.pk1 = t.{pk_col1} AND p.pk2 = t.{pk_col2}
  );
```

5. 检测完成后 `DROP TABLE IF EXISTS tmp_api_pks_{table}`

> **注意**：不使用 `NOT IN`，因为：① 多字段组合 PK 语法不成立；② 大列表性能差；③ NULL 处理有坑。`NOT EXISTS` + 临时表 + 索引是最安全高效的方案。

**改动点**：

| 文件 | 改动 |
|---|---|
| **新建** `ingestion/soft_delete_detector.py` | `SoftDeleteDetector` 类 |
| `schema_manager.py` | `TRACKING_COLUMNS` 增加 `("_deleted_at", "TIMESTAMP")` |
| YAML 配置 | 接口级 `detect_deletes: true/false` |
| `tasks/sync_tasks.py` | 新增 `run_soft_delete_check` RQ 任务 |

### 6.3 YAML 配置扩展

```yaml
interfaces:
  - name: selectOeeReport
    # ... 现有配置 ...
    detect_deletes: false    # MES 报表默认 false；ERP 接口设 true
```

### 6.4 注意事项

- `_deleted_at` 加入 `TRACKING_COLUMNS` 后，**新建的 raw 表自动有此列**；**已有表需迁移**（`ALTER TABLE ADD COLUMN`）
- 软删除检测成本高（需拉全量 PK），建议低频执行（如每周一次）
- 对于 non-time-based 接口，每次全量同步本身就是"最新全量"，可在全量后直接做软删除检测
- **分页策略**：拉取全量 PK 时必须分页（如每页 5000 条），避免单次请求超时。对于十万级以上数据量，按 PK 范围分段拉取
- **性能要求**：十万级数据检测应在 5 分钟内完成；如接口不支持分页或 PK 范围查询，需评估是否适用此方案

## 七、声明式映射层（P3）

### 7.1 问题

数据只到 raw 落地（全部 TEXT 类型，Java 毫秒时间戳未转换）。没有 raw→clean 的转换层。d2a 有完整的 raw→obj 声明式映射（JOIN、值映射、派生列）。

### 7.2 设计概要

> 这块改造量大，后续出独立方案。此处只给方向。

**方向**：
- YAML 声明映射：`backend/config/mappings/{source}.yaml`
- `MappingEngine` 读取配置 → 生成 SQL → 执行 raw→clean 转换
- Clean 表用正确的 PostgreSQL 类型（bigint、numeric、timestamptz 等）
- 支持派生列（如 `duration = end_time - start_time`）、值映射（如 `1→"运行" 2→"停机"`）

```yaml
# config/mappings/MES.yaml 示例
mappings:
  - source_table: raw.mes_select_oee_report
    target_table: clean.mes_oee_report
    pk_fields: [mid, sim_date, shift_name]
    columns:
      mid: bigint
      sim_date: date        # 从 Java 毫秒转换
      shift_name: text
      oee_rate: numeric(5,2)
      run_time: interval
    derived:
      shift_duration: "end_time - start_time"
    lookups:
      machine_name:
        table: raw.mes_get_machine_list
        join_on: mid
        select: machine_name
```

## 九、范式差异提醒（不能照搬 d2a）

| 维度 | d2a（DB直连） | sk-mind（API同步） |
|---|---|---|
| 对账 | `COUNT(*)` 源表，精确 | `total_path` 近似，或分段拉取 |
| 软删除 | `SELECT id FROM 源表` 对比 | 需拉全量 API 数据或专用 PK 接口 |
| Schema 检测 | `information_schema` 直读 | 靠 API 返回的 sample_row 推断 |
| CDC | 可用 SQL Server CDC | 不适用，靠水位 + 回放 |

> **核心原则**：借鉴 d2a 的设计思想（分段对账、隔离区、熔断器、软删除），但实现方式适配 API 场景的约束。
