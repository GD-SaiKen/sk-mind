### B1.2 — Schema 漂移检测：`_check_schema_drift()` 方法

> **依赖**：B1.1（需要 `sync_schema_changes` 表）
> **改动文件**：`backend/app/modules/ingestion/engines/api_sync_engine.py`

#### 目标

当 API 返回的数据包含 DB 表中不存在的列时，自动 `ALTER TABLE ADD COLUMN` 并记录审计。

#### 具体内容

1. 在 `ApiSyncEngine` 中新增 `_check_schema_drift(target_table, sample_row)` 方法
2. 对比 `sample_row` 的 keys（转 snake_case）与 DB 现有业务列
3. 新列 → `ALTER TABLE ... ADD COLUMN IF NOT EXISTS "{col}" TEXT`
4. 写入 `sync_schema_changes` 审计记录
5. 在 `_sync_interface()` 中调用此方法（`_ensure_raw_table()` 之后、`ColumnMapper` 初始化之前），每次同步都检测

> **注意**：不能放在 `_ensure_raw_table()` 内部，因为该方法在表已存在时直接 `return`，不会执行后续代码。

#### 成功标准

- [ ] 已有表 + API 返回新字段时，自动加列，不报错
- [ ] 新列类型为 `TEXT`
- [ ] `sync_schema_changes` 表有对应审计记录
- [ ] 无漂移时不写审计记录，不执行 DDL
- [ ] 已存在的列不会被重复添加

#### 验证方法

```python
# 验证脚本 backend/scripts/verify_schema_drift.py
# 1. 取一条安灯 API 数据，手动加一个假字段 "test_new_field"
fake_row = {"ar_id": "123", "create_date": 1784822400000, "test_new_field": "xxx"}
# 2. 通过 engine 实例调用
engine._check_schema_drift("raw.mes_andon_api_controller", fake_row)
# 3. 断言：
assert "test_new_field" in get_table_columns("raw.mes_andon_api_controller")
assert db.execute("SELECT count(*) FROM sync_schema_changes WHERE column_name = 'test_new_field'").scalar() == 1
# 4. 再调一次，断言不重复添加
engine._check_schema_drift("raw.mes_andon_api_controller", fake_row)
assert db.execute("SELECT count(*) FROM sync_schema_changes WHERE column_name = 'test_new_field'").scalar() == 1
# 5. 清理：ALTER TABLE ... DROP COLUMN test_new_field（用事务回滚更佳）
```

### B1.3 — 对账 L1：捕获 API total + 轻量对账

> **依赖**：B1.1（需要 `sync_reconciliations` 表）
> **改动文件**：`backend/app/modules/ingestion/connectors/api_client.py`、**新建** `backend/app/modules/ingestion/reconciler.py`、`backend/app/modules/ingestion/engines/api_sync_engine.py`

#### 目标

每次同步完成后，按**同步模式分作用域**做轻量对比：全量对比整表行数 `db_count`，增量对比**本批拉取数 `pulled_count`**（不是整表行数，否则窗口总量 vs 整表累计会产生负差异率且掩盖窗口内丢数）。发现差异记录告警。

#### 具体内容

1. `api_client.py`：`fetch_all_pages()` 增加返回 `first_page_total`（从 `total_path` 提取的总量）
2. **新建** `reconciler.py`：`Reconciler` 类，`reconcile_l1(ds_id, interface_name, target_table, api_total, batch_id, sync_mode='full', pulled=0)` 方法（`sync_mode='incremental'` 时 `compared=pulled_count`，`full` 时 `compared=db_count`）
3. `api_sync_engine.py`：`_sync_interface()` 末尾调 `reconcile_l1()`
4. 对账结果写入 `sync_reconciliations` 表（`check_level='L1'`）
5. 差异 > 阈值 → `status='warning'`；差异 = 0 → `status='pass'`

#### 成功标准

- [ ] `fetch_all_pages` 能返回 API 总量（不为 None）
- [ ] 每次同步后 `sync_reconciliations` 表新增一条 L1 记录
- [ ] `api_total` = API 第一页 total 值
- [ ] 全量场景：`db_count` = `SELECT COUNT(*) FROM raw.{table}` 实际值
- [ ] 增量场景：`compared = pulled_count`（本批实际翻页拉取行数），`sync_reconciliations` 记录带 `sync_mode='incremental'` 与 `pulled_count`
- [ ] `diff_count` = `api_total - compared`，计算正确（`compared` 按同步模式取 `db_count` 或 `pulled_count`）
- [ ] 安灯 + OEE 同步后均有对账记录
- [ ] 对账不影响同步主流程（对账异常不中断同步）

#### 验证方法

```python
# 验证脚本 backend/scripts/verify_reconciliation_l1.py
# 1. 执行一次安灯增量同步
# 2. 查 sync_reconciliations
recon = db.execute("""
  SELECT * FROM sync_reconciliations
  WHERE interface_name = 'andonApiController' AND check_level = 'L1'
  ORDER BY checked_at DESC LIMIT 1
""").fetchone()
# 3. 断言
assert recon is not None
assert recon.api_total > 0
assert recon.db_count > 0
# 增量场景 compared = pulled_count；全量场景 compared = db_count
compared = recon.pulled_count if recon.sync_mode == 'incremental' else recon.db_count
assert recon.diff_count == recon.api_total - compared
assert recon.status in ('pass', 'warning')
# 4. 手动验证（全量场景）：SELECT COUNT(*) FROM raw.mes_andon_api_controller 等于 recon.db_count
#    增量场景则应与本批拉取数一致：本批窗口条件下 COUNT ≈ recon.pulled_count
```

### B1.5 — YAML 配置扩展：reconciliation 段

> **依赖**：B1.3
> **改动文件**：`backend/config/data_sources/MES.yaml`、`reconciler.py`（读取配置）

#### 目标

在 YAML 接口配置中声明对账参数，使对账行为可配置化。

#### 具体内容

1. MES.yaml 每个接口增加 `reconciliation` 段：
   ```yaml
   reconciliation:
     enabled: true
     threshold_pct: 5
     auto_repair: false
   ```
2. `Reconciler` 读取配置，`enabled=false` 时跳过对账
3. `threshold_pct` 控制告警阈值
4. `auto_repair=true` 时 L1 差异超阈值自动触发 L2

#### 成功标准

- [ ] `reconciliation.enabled=false` 的接口同步后不产生对账记录
- [ ] `threshold_pct=5` 时，差异率 0% → `status=pass`，差异率 3% → `status=warning`，差异率 6% → `status=failed`
- [ ] `auto_repair=true` 时差异超阈值自动触发 L2（L2 实现后验证）
- [ ] 缺少 `reconciliation` 段时默认 `enabled=true, threshold_pct=5, auto_repair=false`

#### 验证方法


### B2.1 — 定时调度器模块

> **依赖**：无
> **改动文件**：**新建** `backend/app/modules/ingestion/scheduler.py`、**新建** `backend/run_scheduler.py`

#### 目标

实现 APScheduler 集成的定时调度器，到点自动把同步任务入 RQ 队列。

#### 具体内容

1. `scheduler.py`：`SyncScheduler` 类
   - `start()`：从 DB 加载 `schedule_type='cron' AND status='active'` 的任务，注册 APScheduler job；同时启动 60 秒 DB 轮询（`_sync_from_db`）
   - `register(task_id, cron_expr)`：动态注册（5段式 Cron）
   - `unregister(task_id)`：动态注销
   - `_sync_from_db()`：扫描 DB 对齐 jobstore（新增/修改/删除）
   - `_enqueue_sync(task_id)`：到点回调，创建 batch + 入 RQ 队列
   - `max_instances=1, coalesce=True`
2. `run_scheduler.py`：启动脚本（与 `run_worker.py`/`run_api.py` 同级，`backend/` 根目录，git 跟踪）
3. 内存 jobstore，重启从 DB 重新加载

#### 成功标准

- [ ] 调度器能启动，不报错
- [ ] DB 中 `schedule_type='cron'` 的任务被加载并注册
- [ ] 到点后自动入队 RQ，Worker 能消费执行
- [ ] 同一任务不会重叠执行（`max_instances=1`）
- [ ] 手动修改 `cron_expression` 后，重新注册生效
- [ ] 调度器进程独立于 API 和 Worker

#### 验证方法

```python
# 验证脚本 backend/scripts/verify_scheduler.py
# 1. 在 DB 中创建一个 schedule_type='cron', cron_expression='*/1 * * * *' 的任务（每分钟）
# 2. 启动 scheduler: python run_scheduler.py
```

## 通用验收原则

> **每个任务合并前必须满足**：

1. **不破坏现有功能**：安灯 + OEE 同步仍正常工作（每轮开发结束后做一次回归验证）
2. **不引入新依赖冲突**：`pip freeze` / `npm ls` 无异常
3. **有验证脚本或验证步骤**：可复现的验证方法
4. **日志友好**：新增逻辑有合理的 `logger.info`/`warning` 输出
5. **异常安全**：新增逻辑的异常不中断主流程（同步/页面加载），关键路径加 `try/except`；对账/隔离区写入失败时需在单元测试中模拟异常场景（如表不存在），验证同步不中断
6. **类型安全**（前端）：`vue-tsc --noEmit` 无新增错误
7. **单元测试**（后端）：新增的后端方法应有单元测试覆盖，至少覆盖正常路径和异常路径
8. **迁移可回滚**（涉及 DDL 的任务）：Alembic 迁移文件需同时提供 `upgrade()` 和 `downgrade()`，且 `alembic downgrade -1` 能成功回退
