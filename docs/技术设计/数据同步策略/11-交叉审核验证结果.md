#### 3. L1 对账的 `total` 语义未明确 — ✅ 确认存在（需实验验证）

**代码证据**：`api_client.py` 第 159-201 行，`fetch_page()` 从 `total_path` 提取 `total` 并放入 `ApiPageResult`：

```python
total = self._extract_nested(data, self._total_path)
return ApiPageResult(
    records=records if isinstance(records, list) else [],
    total=total if isinstance(total, int) else None,
    ...
)
```

但 `fetch_all_pages()` 第 203-225 行只 `yield from result.records`，**完全不捕获 `total`**：

```python
def fetch_all_pages(self, ...):
    while True:
        result = self.fetch_page(endpoint, method, params, body, page, page_size)
        yield from result.records  # ← total 被丢弃
        if len(result.records) < page_size:
            break
```

**关键问题**：MES API 返回的 `total` 是"当前查询条件（含日期参数）下的总数"还是"全量总数"？这决定了 L1 对账的合理性。

- 如果 `total` 受日期参数过滤 → 与增量同步后的 DB 行数对比**合理**
- 如果 `total` 不受过滤 → 与增量 DB 行数对比**不公平**，会频繁误报

**修正**：08 方案 2.2 节增加说明：
> 在实现 L1 对账前，**必须先验证 MES API 的 `total` 是否随日期参数变化**。验证方法：用不同日期范围调接口，看 `total` 是否不同。如果 `total` 不随日期变化，则 L1 只能在全量同步后做，增量同步后不做 L1。

### 重要问题

#### 4. Schema 漂移调用时机表述矛盾 — ✅ 确认存在

**代码证据**：`api_sync_engine.py` 第 159-200 行，`_ensure_raw_table()` 在表已存在时**直接 return**：

```python
def _ensure_raw_table(self, target_table: str, sample_row: dict) -> None:
    if target_table in self._ensured_tables:
        return
    # ...
    exists = self._db.execute(check, ...).scalar_one()
    if exists:
        self._ensured_tables.add(target_table)
        return  # ← 已有表：什么都不做就返回
```

08 方案说"在 `_ensure_raw_table` 末尾调用"漂移检测，但对已有表，`_ensure_raw_table` 在 return 之前不会执行末尾的代码。

**修正**：明确调用位置为 `_sync_interface()` 中，`_ensure_raw_table()` 调用之后、`ColumnMapper` 初始化之前：

```python
# api_sync_engine.py _sync_interface() 中
self._ensure_raw_table(target_table, rows[0])
# ↓ 新增：每次同步都检测漂移（用实际返回的第一行作为 sample）
self._check_schema_drift(target_table, rows[0])
mapper = ColumnMapper(self._get_table_business_columns(target_table))
```

#### 5. `_source_id` 过滤缺失 — ⚠️ 部分成立（非错误，但多余）

**代码证据**：raw 表是按接口分表的（YAML 中 `target_table` 指定，如 `raw.mes_andon_api_controller`）。每张表只存一个接口的数据，`_source_id` 虽然是 tracking column，但同表数据通常来自同一数据源。

08 方案 L1 对账写 `SELECT COUNT(*) FROM raw.{table} WHERE _source_id = :ds`，这个 `WHERE` 条件**不会报错**，但**是多余的**（一张表只有一个数据源的数据）。

**修正**：去掉 `WHERE _source_id = :ds`，简化为 `SELECT COUNT(*) FROM raw.{table}`。

---

#### 6. 调度器与 API 进程的联动机制未设计 — ✅ 确认存在

**分析**：APScheduler 使用 `MemoryJobStore`（08 方案 4.3 节），运行在 `run_scheduler.py` 独立进程中。router 在 API 进程中，两者**不共享内存**。router 调 `scheduler.register()` 时，调用的是 API 进程内存中的对象，**不会影响 scheduler 进程**。

**修正**：08 方案 4.2 节补充联动机制设计，建议方案：

> **方案 A（推荐）：DB 轮询**
> - scheduler 每 60 秒扫描 `IngestionTask` 表，对比 DB 中的 cron 任务和内存 jobstore 中的 job
> - 新增/修改/删除的任务自动同步到 jobstore
> - 优点：简单可靠，无需额外通信组件
> - 缺点：最多 60 秒延迟

> **方案 B：Redis pub/sub**
> - router 修改任务后发 Redis 消息 `scheduler:reload`
> - scheduler 监听消息，收到后重新加载
> - 优点：实时
> - 缺点：多一个通信通道

建议用方案 A，60 秒延迟对同步任务完全可接受。

### 重要问题

#### 4. `QuarantineRecord` 类型字段对齐 — ⚠️ 需确认后端返回格式

**分析**：`sync_quarantine.raw_json` 在 DB 中是 `JSONB` 类型。后端用 `CamelModel` 序列化时，JSONB 字段可能返回为 object（如果 Pydantic 做 JSON 解析）或 string（如果直接返回）。

前端类型定义为 `rawJson: string` 并在模板中 `JSON.parse(quarantineRow.rawJson)`。如果后端返回的已经是 object，`JSON.parse` 会报错。

**修正**：实现时需确认后端 schema 的返回类型。建议前端类型改为 `rawJson: string`，后端 API 返回时确保 `raw_json` 序列化为 JSON 字符串（`json.dumps`），前端再 `JSON.parse`。或前端类型改为 `Record<string, unknown>`，直接用不解析。
