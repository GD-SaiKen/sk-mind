## 文档说明

本文档补全 [[01-数据同步策略总览]] 中未充分展开的三大核心机制：

1. **增量更新（对比机制）**：如何判断一条数据是"新增"、"变更"还是"删除"
2. **时间范围更新策略**：从哪个时间点到哪个时间点拉取数据（全量从系统上线日到昨天、默认近期 30 天等）

## 1. 增量更新 — 对比机制

增量更新的核心问题是：**源端数据发生了哪些变化（新增/修改/删除），如何精准识别并写入平台？**

### 1.1 三种增量识别策略

| 优先级 | 策略 | 原理 | 适用条件 | 精度 |
|---|---|---|---|---|
| **1** | 时间戳增量 | `WHERE modify_time > :last_sync_time` | 源表有时间戳字段（`MODIFY_DATE`、`UPDATE_TIME` 等） | 高（精确到行） |
| **2** | 自增主键增量 | `WHERE id > :last_max_id` | 仅追加不修改的表（日志/流水类） | 中（无法感知 UPDATE） |
| **3** | Hash 对比兜底 | 全量拉取 → 逐行 hash → 与已有 hash diff | 无时间戳、无自增主键、数据量小 | 高（但全量拉取开销大） |

> **注意**：两种同步策略（数据库视图同步 / API 拉取同步）均可使用上述三种增量策略，但 API 拉取额外依赖接口自身是否支持 `startTime`/`endTime` 参数。若接口不支持增量查询参数，只能走策略 3（全量 + hash 去重）。

### 1.2 时间戳增量流程（优先级最高）

```text
┌──────────────────────────────────────────────────────────────┐
│ 增量同步流程（时间戳模式）                                      │
│                                                              │
│ ① 读取上次同步时间                                             │
│    从 IngestionTask.last_sync_time 读取                       │
│    若从未同步过（last_sync_time = NULL），由用户决定：          │
│    ├── 执行全量同步（推荐）                                    │
│    └── 手动指定起始时间（如"2024-01-01"）                      │
│                                                              │
│ ② 构建时间窗口                                                │
│    start_time = last_sync_time（上次成功同步的结束时间）        │
│    end_time   = NOW()（当前时间）                              │
│    → 如需避免因延迟数据漏拉，增加 5 分钟缓冲：                  │
│      start_time = last_sync_time - 5min                      │
│                                                              │
│ ③ 拉取变更数据                                                │
│    DB 同步:                                                   │
│      SELECT * FROM {table}                                    │
│      WHERE {timestamp_col} > :start_time                      │
│        AND {timestamp_col} <= :end_time                       │
│      ORDER BY {timestamp_col}                                │
│    API 同步:                                                  │
│      POST /api/endpoint                                       │
│      body: { startTime: start_time, endTime: end_time, ... } │
│                                                              │
│ ④ 逐行对比与写入                                              │
│    对每条记录计算 _source_row_hash                             │
│    ├── hash 不存在于 Raw 层 → INSERT（新增行）                 │
│    ├── hash 已存在但内容不同 → INSERT + 标记旧行 _is_stale     │
│    └── hash 相同 → SKIP（未变化）                              │
│                                                              │
│ ⑤ 感知删除（可选）                                            │
│    若源表支持「软删除标记」（如 is_deleted 字段）：              │
│    SELECT * WHERE {timestamp_col} > :start_time               │
│    → 含 is_deleted = true 的行 → 标记平台侧 _is_deleted        │
│    若源表是硬删除（物理删除），以 hash 对比兜底检测              │
│                                                              │
│ ⑥ 更新 last_sync_time                                        │
│    写入 end_time 到 IngestionTask.last_sync_time              │
│    记录到 IngestionBatch 的 started_at / finished_at          │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 Hash 对比机制（三种策略的通用兜底）

Hash 对比是增量更新的**最底层兜底机制**。无论用时间戳还是自增主键，最终都通过 hash 判断数据是否真的有变化。

```text
┌──────────────────┐
│ 源端数据行        │ → SHA-256(payload 序列化) → _source_row_hash
│ {col1, col2, ...}│   取前 16 位（40 亿分之一碰撞概率，可接受）
└──────────────────┘

对比流程（每次增量写入时）:

① 拉取的每一行 → 计算 hash
② 查询 Raw 层同 _source_object 的最新 hash 集合
   SELECT _source_row_hash FROM {raw_table}
   WHERE _source_object = :obj
     AND _is_deleted = FALSE
     AND _batch_id IN (最近 3 个批次的 batch_id)
③ diff 结果:
   ┌─────────────────────┬──────────┬──────────────────┐
   │ 情况                │ 判断     │ 操作             │
   ├─────────────────────┼──────────┼──────────────────┤
   │ 源有，平台无        │ 新增     │ INSERT           │
   │ 源有，平台有，hash同│ 无变化   │ SKIP             │
   │ 源有，平台有，hash异│ 变更     │ INSERT（新版本）  │
   │ 平台有，源无        │ 源端删除 │ UPDATE _is_deleted │
   │                     │          │ = TRUE（不物理删）│
   └─────────────────────┴──────────┴──────────────────┘
```

> **说明**：`_is_deleted = TRUE` 而不是物理 DELETE，是为了保留数据溯源能力。Clean 层和 Serving 层根据 `_is_deleted` 过滤已删除数据。

### 1.4 源端"硬删除"的检测

当源端是物理删除（数据行彻底消失，没有 is_deleted 标记）时：

| 方式 | 原理 | 开销 | 适用 |
|---|---|---|---|
| **全量 hash 对比** | 拉取全量 → 计算每条 hash → 与平台最近批次的 hash 集合做差集 | 高（需全量拉取） | 仅小表（< 1 万行，如配置表） |
| **不主动检测** | 接受"平台多出历史行" | 无 | 大表（百万级），业务可接受少量过期数据 |
| **定期全量覆盖** | 每周/每月一次全量同步（覆盖模式），自然消除已删数据 | 中 | 中大型表，定期核对 |

**推荐策略**：对大表不主动检测硬删除，依赖定期全量覆盖（如每月第一个周日凌晨全量同步一次，以"覆盖模式"重建 Raw 表数据）。

## 2. 时间范围更新策略

### 2.1 核心概念

时间范围策略回答"**从哪个时间开始，拉到哪个时间为止**"。

```text
                    ┌── 系统上线日（用户配置）
                    │
    ────────────────┼──────────────┬───────────────┬──────→ 时间轴
                    │              │               │
                    ▼              ▼               ▼
              全量回溯范围      常规增量范围      未来
              (history_start)   (last_sync→now)
```

### 2.2 三种时间范围模式

| 模式 | 时间范围 | 触发时机 | 典型用途 |
|---|---|---|---|
| **全量回溯** | `history_start_date → 昨天 23:59:59` | 首次接入、手动触发 | 系统初次接入时补全历史数据 |
| **常规增量** | `last_sync_time → NOW()` | 定时任务（每日） | T+1 日常增量 |
| **近期快补** | `NOW() - N天 → NOW()` | 手动触发、故障恢复 | 补最近 N 天的数据（如接口故障导致漏拉） |

### 2.3 全量回溯策略

全量回溯（首次接入或手动触发"补全历史"）的时间范围：

```text
start_time = history_start_date   ← 用户在数据源配置中设定的"系统上线日期"
                                   （默认：2020-01-01，可修改）
end_time   = TODAY - 1 天          ← 不包含今天（今天的数据由增量覆盖）

示例：用户设定 ERP 上线日期为 2024-06-01，今天是 2026-07-13
→ 全量回溯范围: 2024-06-01 00:00:00 ~ 2026-07-12 23:59:59
```

**分窗口执行**（针对 API 拉取，接口有时间范围查询限制）：

```python
# API 全量回溯：按天分窗口
def build_time_windows(start: datetime, end: datetime, window_days: int = 1):
    """将大范围拆分为每日窗口，匹配 MES API 的 24h 限制"""
    current = start
    while current < end:
        window_end = min(current + timedelta(days=window_days), end)
        yield (current, window_end)
        current = window_end

# 示例：365 天 → 365 个窗口，每窗口一次 API 请求
```

### 2.4 常规增量策略（定时触发）

定时任务触发时的**默认时间范围**：

```text
┌────────────────────────────────────────────────────────────────┐
│ 定时任务执行时间: 每日凌晨 01:00                                  │
│                                                                │
│ 拉取范围: 昨天 00:00:00 → 昨天 23:59:59（或 last_sync → NOW）   │
│                                                                │
│ 示例: 2026-07-13 01:00 触发的定时任务                            │
│ → 拉取 2026-07-12 00:00:00 → 2026-07-12 23:59:59 的数据         │
│                                                                │
│ 若任务因故未能执行（如 Worker 宕机），下一次执行时自动补齐：       │
│ → last_sync_time 停留在 2026-07-11 01:00                        │
│ → 2026-07-14 01:00 触发时                                       │
│ → 拉取 2026-07-11 01:00 → 2026-07-14 00:00 的数据               │
│   （包含了 7/12 和 7/13 的数据，自动补齐漏拉）                    │
└────────────────────────────────────────────────────────────────┘
```

**时间范围计算规则**（后端服务层实现）：

```python
def calc_incremental_time_range(
    task: IngestionTask,
    now: datetime,
) -> tuple[datetime, datetime]:
    """
    计算增量同步的时间范围。

    规则：
    1. 若 task.last_sync_time 为 NULL（首次增量）：
       → 默认拉取最近 30 天
       → start = now - 30 days
    2. 若 task.last_sync_time 存在：
       → start = last_sync_time - buffer（5 分钟缓冲避免边界遗漏）
    3. end = now（当前时间）
    4. 若 start 早于 history_start_date，以 history_start_date 为准
    """
    buffer = timedelta(minutes=5)

    if task.last_sync_time is None:
        # 首次增量：拉最近 30 天
        start = now - timedelta(days=30)
    else:
        start = task.last_sync_time - buffer

    # 不早于系统上线日期
    history_start = _get_history_start_date(task)
    if history_start and start < history_start:
        start = history_start

    end = now
    return start, end
```

### 2.5 近期快补策略

当用户发现数据缺失（如接口故障导致某几天数据漏拉），手动触发"近期快补"：

| 快补选项 | 时间范围 | 前端入口 |
|---|---|---|
| 昨天 | `昨天 00:00 → 昨天 23:59` | 一键"补拉昨天" |
| 最近 7 天 | `7 天前 → 昨天` | 一键"补拉本周" |
| 最近 30 天 | `30 天前 → 昨天` | 一键"补拉本月" |
| 自定义 | 用户选择起止日期 | 日期选择器 |

> **说明**：快补复用全量同步逻辑，仅时间范围不同。快补期间不更新 `last_sync_time`（避免影响日常增量）。

### 2.6 配置模型扩展

为支持时间范围策略，需在 `IngestionTask.config` JSON 中扩展以下字段：

```json
{
  "sync_mode": "incremental",
  "incremental_column": "MODIFY_DATE",
  "time_window_days": 1,
  "history_start_date": "2024-06-01",
  "buffer_minutes": 5,
  "default_recent_days": 30
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sync_mode` | `"full"` / `"incremental"` | 同步模式 |
| `incremental_column` | string | 增量字段名（时间戳列或自增 ID 列） |
| `time_window_days` | int | 定时任务每次拉取的天数窗口（默认 1） |
| `history_start_date` | date | 系统上线日期，全量回溯的起始点 |
| `buffer_minutes` | int | 时间缓冲（分钟），避免边界数据遗漏（默认 5） |
| `default_recent_days` | int | 首次增量时默认拉取最近 N 天（默认 30） |

## 3. 定时同步任务

### 3.1 架构总览

```text

│                     定时调度架构                             │
│                                                             │
│  ┌──────────────┐     ┌──────────────────┐                  │
│  │ APScheduler   │ →   │ TaskService      │                  │
│  │ (FastAPI 内)  │     │ trigger_scheduled │                  │
│  │              │     │ _sync()          │                  │

│  └──────────────┘              │                            │
│                                │ 创建批次 + RQ 入队          │
│                                ▼                            │
│  ┌──────────────┐     ┌──────────────────┐                  │
│  │ RQ Worker    │ ←── │ Redis Queue       │                  │
│  │              │     │ "ingestion"       │                  │
│  │ 执行同步     │     └──────────────────┘                  │
│  └──────┬───────┘                                           │

│  ┌──────────────┐                                           │

```

### 3.2 调度表达式（Cron）

| Cron 表达式 | 含义 | 用途示例 |
|---|---|---|
| `0 1 * * *` | 每日凌晨 01:00 | 拉取昨天的数据（T+1 日间增量） |
| `0 2 * * *` | 每日凌晨 02:00 | ERP 主数据增量 |
| `0 3 * * *` | 每日凌晨 03:00 | ERP 交易表增量 |
| `0 4 * * *` | 每日凌晨 04:00 | ERP 流水表增量 |
| `0 2 * * 0` | 每周日凌晨 02:00 | 配置表全量覆盖 |
| `0 */1 * * *` | 每小时整点 | MES 三色灯（实时性高） |
| `30 2 * * *` | 每日凌晨 02:30 | MES 工单增量（错开 ERP 高峰） |

### 3.3 时间窗口计算（定时触发的动态范围）

定时任务触发时，不总是拉"昨天"。时间范围根据**任务类型**和**执行时间**动态计算：

```python
def calc_scheduled_time_range(
    task: IngestionTask,
    trigger_time: datetime,
) -> tuple[datetime, datetime]:
    """
    定时任务触发时，动态计算应拉取的时间范围。

    核心规则：
    ┌─────────────────────┬─────────────────────────────────┐
    │ schedule_type       │ 时间范围                         │
    ├─────────────────────┼─────────────────────────────────┤
    │ 每日 cron（含周/月） │ last_sync_time → trigger_time   │
    │ 首次执行            │ history_start → yesterday 23:59  │
    │ 手动触发            │ 由前端传入 start / end            │
    │ 快补触发            │ 由前端传入 start / end            │
    └─────────────────────┴─────────────────────────────────┘

    对于"每日凌晨 01:00 拉取昨天"这个场景：
    - last_sync_time = 2026-07-12 01:00:00
    - trigger_time   = 2026-07-13 01:00:00
    - 实际拉取范围 = [2026-07-12 01:00:00, 2026-07-13 01:00:00]
    - 即包含了 7/12 全天的数据
    """
    if task.last_sync_time is None:
        # 首次定时触发：从系统上线日开始
        history_start = _parse_date(task.config.get("history_start_date"))
        start = history_start or (trigger_time - timedelta(days=30))
        end = trigger_time.replace(hour=0, minute=0, second=0)  # 今天 00:00，即昨天结束
    else:
        start = task.last_sync_time - timedelta(
            minutes=task.config.get("buffer_minutes", 5)
        )
        end = trigger_time

    return start, end
```

### 3.4 各系统同步时段编排

避免多个系统同时同步导致资源争抢。编排原则：

1. **先主数据，后交易数据**：确保外键引用的主数据先就位
2. **错开各系统高峰**：不同系统间隔至少 30 分钟
3. **大表放凌晨低峰**：流水表、日志表等大数据量表放在凌晨 3:00-5:00
4. **同系统内 Phase 编排**（已在 02 文档 §8.2 定义）

```text
时段          ERP                      MES                  SRM
────────────────────────────────────────────────────────────────────
00:00-00:30   —                       —                    —
00:30-01:00   —                       —                    —
01:00-02:00   P0主数据增量             —                    P0基础资料全量
02:00-03:00   P0交易表增量             P0工单/报工增量       —
03:00-04:00   P0流水表增量             P0设备OEE增量         P0交易数据全量
04:00-05:00   大表/历史补充            —                    P1数据
05:00-06:00   Clean层触发              Clean层触发          Clean层触发
06:00-07:00   —                       —                    —
（白天）      每小时: MES三色灯状态     每小时: MES三色灯     —
（周日）      凌晨: 配置表全量覆盖      凌晨: 物料全量        凌晨: 工作台配置全量
```

  let start: string, end: string;

  switch (preset) {

      end = dayjs().subtract(1, "day").endOf("day").toISOString();
      break;
    case "7days":
      start = dayjs().subtract(7, "day").startOf("day").toISOString();
      end = dayjs().subtract(1, "day").endOf("day").toISOString();
      break;
    case "30days":
      start = dayjs().subtract(30, "day").startOf("day").toISOString();
      end = dayjs().subtract(1, "day").endOf("day").toISOString();
      break;
    case "custom":
      // 用户从日期选择器选择
      start = customStartDate;
      end = customEndDate;
      break;
  }

  const { batchId } = await api.post(`/api/ingestion-tasks/${taskId}/quick-fill`, {

    endTime: end,
  });
  startProgressPolling(batchId);
}

# app/modules/ingestion/router.py 新增端点

@task_router.post("/{task_id}/backfill")
async def backfill_task(
    task_id: uuid.UUID,
    db: AsyncSession = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
    """全量回溯：从系统上线日期拉取全量数据至今"""
    task = await dao.task_get_by_id(db, task_id)
    if not task:
        raise HTTPException(status_code=404, detail="not found")

    # 计算时间范围
    history_start = _parse_history_start(task.config)
    end_time = datetime.now(timezone.utc).replace(hour=0, minute=0, second=0)

    # 创建批次并提交 RQ
    batch = IngestionBatch(
        task_id=task.id, trigger_type="backfill",
        status="pending", triggered_by=str(current_user.id),
    )
    await dao.batch_insert(db, batch)

    try:
        from app.core.queue import redis_conn
        from rq import Queue
        queue = Queue("ingestion", connection=redis_conn)
        job = queue.enqueue(
            "app.modules.ingestion.tasks.sync_tasks.run_backfill_sync",
            str(task.id), str(batch.id),
            history_start.isoformat(), end_time.isoformat(),
            job_timeout=7200  # 2 小时超时
        )
        batch.status = "running"
        batch.started_at = datetime.now(timezone.utc)
        await dao.batch_update(db, batch)
        return _ok({
            "batchId": str(batch.id), "jobId": job.id,
            "startTime": history_start.isoformat(),
            "endTime": end_time.isoformat(),
        }, msg="全量回溯已提交")
    except Exception as e:
        batch.status = "failed"
        batch.error_summary = f"enqueue failed: {e}"
        await dao.batch_update(db, batch)
        raise HTTPException(status_code=500, detail=str(e))

### 5.2 漏拉/重复拉的保护机制

| 场景 | 保护机制 |
|---|---|
| 定时任务执行时 Worker 宕机 | RQ Job 超时后自动标记失败，下一轮 `last_sync_time` 未更新，自动重拉 |
| 增量拉取时边界数据遗漏 | 5 分钟缓冲 (`last_sync_time - 5min`)，确保边界数据被覆盖 |
| 同一条数据被多次拉取 | `_source_row_hash` 去重约束，`ON CONFLICT DO NOTHING` |
| 源端时间回拨（修正历史数据） | hash 对比机制可感知内容变化，不依赖时间戳的正确性 |
| 漏拉多天（Worker 宕机 3 天） | `last_sync_time` 停留在 3 天前，下一次自动拉取 3 天的数据 |
