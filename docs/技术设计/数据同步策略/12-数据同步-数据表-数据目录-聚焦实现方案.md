# 数据同步 → 数据表 → 数据目录 — 聚焦实现方案

> 本方案聚焦三个模块的完整链路打通，基于 [[数据表与数据目录-完整实现方案]] 的设计框架。
>
> 每个任务描述的是**用户最终能看到什么、能做什么**。字段不提前加，哪个任务需要就加在哪个任务里。

## 一、三个模块分别是什么

### 数据同步（已实现 90%）

系统从 MES API 拉取数据，经过校验、去重、upsert，最终写入 PostgreSQL 物理表（raw 层）。同步引擎负责"怎么拉、怎么存"。

**当前有一个关键缺口**：数据写完就完了，系统不知道自己多了哪些表、这些表有什么字段。后面的数据表模块和目录模块自然也就看不到它。

### 数据表模块（技术视角，55% 完成）

面向**数据负责人和技术人员**。回答这些问题：
- 平台里现在有哪些数据表？每张表有多少行、多少字段？
- 字段是什么类型、是否可以为空？
- 哪些字段是主键？这张表从哪个数据源来的？
- 质量状态是否正常？

### 数据目录模块（业务视角，10% 完成）

面向**业务用户和 AI Agent**。回答这些问题：
- 平台有哪些数据可以用？这些数据的业务含义是什么？
- 有没有我要找的那个字段？它属于哪个数据集？
- Agent 能不能查这张表？有什么限制？

数据目录不建独立数据表——它是数据表元数据 + 质量状态 + 血缘关系的**聚合展示层**。

> **对照原型说明文档**：
> 数据表模块 = [[../产品方案/03-页面原型说明#8. 数据表模块|原型§8]]
> 数据目录模块 = [[../产品方案/03-页面原型说明#9. 数据目录模块|原型§9]]

### 三者的关系

```
数据同步（MES API → raw 物理表）
       ↓ 自动注册
数据表模块（技术视角：维护元数据、补充字段说明）
       ↓ 聚合展示
数据目录模块（业务视角：浏览可用数据、搜索字段）
       ↓ 查询支撑
AI Agent（query_objects 发现数据、受控查询）
```

## 二、当前核心断点

一句话：**同步引擎写完 raw 表后，没有登记元数据。**

具体表现：
- 数据表列表页是空的——因为没有自动创建 Dataset 记录
- 数据目录自然也是空的——因为它只是聚合展示，底层没数据
- Agent 无法发现任何可查询的数据集

打通之后的效果：
- 同步完成 → 数据表列表自动出现新表 → 字段列表已有物理列信息 → 数据目录可浏览 → Agent 可发现

## 三、现有模型盘点（T2 启动前先看清有什么）

启动 T2 之前，先搞清楚 Dataset 和 DatasetField 已经有哪些字段可用。

### Dataset 现有字段

| 字段 | 类型 | T2 怎么用 |
|---|---|---|
| name | varchar(200) | 暂用 target_table 填（ `raw.mes_filter_workorder` ） |
| code | varchar(100) unique | 同 target_table |
| description | text | 暂不填，后续可选从 YAML 补 |
| data_layer | varchar(20) | 固定 `raw` |
| data_source_id | uuid | 从当前同步任务关联的数据源取 |
| record_count | int | `information_schema` 统计 |
| field_count | int | `information_schema` 统计 |
| business_domain | varchar(100) | 从 YAML 注释分组推断（如 `# ── 工单域 ──`） |
| is_agent_accessible | bool | 默认 `false`（数据负责人检查后再开） |
| status | varchar(20) | 固定 `active` |

**T2 不需要给 Dataset 加任何新字段**，现有字段已经够用。

### DatasetField 现有字段

| 字段 | 类型 | T2 怎么用 |
|---|---|---|
| field_name | varchar(200) | 物理列名 |
| field_alias | varchar(200) | 暂不填，后续可选优化 |
| description | text | 暂不填 |
| data_type | varchar(50) | `information_schema` 读取 |
| field_length | int | `information_schema` 读取 |
| is_nullable | bool | `information_schema` 读取 |
| ordinal_position | int | `information_schema` 读取 |
| sensitivity_level | varchar(20) | 默认 `internal` |
| quality_status | varchar(20) | 默认 null |
| sample_values | text | 暂不填 |

**T2 缺少 2 个字段**——这就是 T1 的全部内容：

| 缺失字段 | 作用 |
|---|---|
| is_primary_key | 标记这个字段来自 YAML `pk_fields`，写入时 ON CONFLICT 用它 |
| source_column | raw 表的列名即源字段名。对 raw 层来说两者一样，但对 clean/serving 层追溯来源有用 |

## 四、任务拆分

### T1：字段表补充 is_primary_key 和 source_column

**用户现在面临的困境**：
- 同步完成后字段列表里有所有物理列，但不知道哪些是主键
- 无法追溯字段的原始来源

**做完后 T2 可以用的能力**：
- DatasetField 上多了两个标记字段，T2 注册时自动填写

**验收**：执行迁移后 `dataset_fields` 表多了 `is_primary_key` 和 `source_column` 两个列，不影响已有数据。已有 API 不报错。

---

### T2：同步完成后自动登记数据表

**用户现在面临的困境**：
- MES API 已经同步了好几轮，物理表里已经有数据了
- 但打开「数据表」列表页，什么也看不到

**做完后用户感受到的变化**：

每次同步成功后，打开「数据表」列表页，**自动出现一条记录，基本信息已经填好**：

| 自动填充的内容 | 从哪里来 | 填到哪个字段 |
|---|---|---|
| 表名 | YAML `target_table` | `name`, `code` |
| 业务域 | YAML 中该接口上方最近的 `# ── XX域 ──` 注释 | `business_domain` |
| 来源数据源 | 当前同步任务的数据源 ID | `data_source_id` |
| 分层 | 固定 raw | `data_layer` |
| 状态 | 固定 active | `status` |
| 记录数 / 字段数 | `information_schema` | `record_count`, `field_count` |
| 字段名、类型、是否可空、序号 | `information_schema.columns` | `field_name`, `data_type`, `is_nullable`, `ordinal_position` |
| 主键标记 | YAML `pk_fields` 列表匹配 | `is_primary_key` |
| 源列名 | 物理列名（raw 层即源） | `source_column` |

现有字段全部够用——不需要给表加任何新字段。T1 加的 `is_primary_key` 和 `source_column` 是最小必要新增。

**关键行为规则**：

| 场景 | 行为 |
|---|---|
| 首次同步某接口 | 创建 Dataset + DataTable + 全部 DatasetField，自动填充 |
| 增量同步，字段没变 | 只更新 record_count、field_count、updated_at |
| 增量同步，物理表多了新列 | 新增缺失的字段并自动填充；已有字段不动 |
| 注册过程出错 | 不影响同步主流程，同步仍成功，只记日志 |

**YAML 增强建议**（可选，不加也能跑）：
```yaml
interfaces:
  - name: filterWorkorder
    display_name: "工单筛选"     # 可选，不加则 name 直接填入
    description: "按时间和状态查询工单列表"  # 可选
```

**验收**：
- 执行一次同步 → 打开「数据表」→ 看到自动登记的新表
- 详情页字段列表有正确列名、主键标记、源列名
- 再执行一次同步：不产生重复记录
- 手动删掉 Dataset 后再次同步：自动重建

### T3：同步引擎接入桥接逻辑

**是什么**：把 T2 的自动登记逻辑嵌入到同步引擎的实际执行流程中。

**验收**：在「接入任务」页面执行一次任务 → 去「数据表」列表页 → 记录已出现。全链路打通。

---

### T4：数据表列表筛选和字段打标

**用户现在面临的困境**：
- 列表页筛选大部分不生效（来源、质量过了还是全量）
- 数据负责人想 review 自动登记的结果、标记敏感字段，但没有便捷入口

**做完后用户能看到什么**：

列表筛选全部生效：
- 按「来源数据源」筛
- 按「业务域」筛（工单/设备/物料/…）
- 按「状态」筛（active/draft/archived）
- 按「Agent 可用」筛
- 关键词搜索（同时匹配 name、description）

字段 review 和打标：
- 打开数据表详情 → 字段列表已自动填充（T2 做的）
- 数据负责人快速扫一遍，主要做两件事：
  - 标敏感字段：勾选含隐私数据的字段 → 点"批量标记为敏感"
  - 改显示名：个别字段改得更准确（已有 `field_alias` 字段可用）
- 批量操作：勾选多个字段一起切换 sensitivity_level / 开关 Agent 查询权限

样例数据预览：
- 详情页「样例数据」Tab 展示物理表前 100 行（排除系统 tracking 列）
- 帮助判断"这个字段实际存的是什么"，决定要不要标敏感

**本任务不需要加新字段**——sensitivity_level、field_alias、description 都是现成的。

**验收**：
- 列表页每个筛选项选完结果正确变化
- 批量改 sensitivity_level：勾选 3 个字段 → 标记敏感 → 刷新确认
- 样例数据 Tab 显示真实数据行

---

### T5：字段空值率统计

**用户现在面临的困境**：
- 不知道哪些字段数据缺失严重

**做完后用户能看到什么**：
- 字段列表每行显示空值率百分比（如 `remark` 空值率 87%）
- 一眼发现数据缺失的字段

**新增字段**：仅为空值率增加一个字段。其他统计指标（质量状态）留到质量模块完整对接时再做。

| 新增字段 | 写在哪个表 | 业务含义 | 谁算 |
|---|---|---|---|
| null_rate | dataset_fields（新建） | 该字段 null 值占比 | 按需统计任务：`SELECT count(*) FILTER(WHERE col IS NULL) * 100.0 / count(*)` |

**验收**：字段列表显示空值率，与直接查物理表的结果一致。

---

### T6：Agent 可用性检查

**用户现在面临的困境**：
- 不知道一张表能不能安全地开放给 Agent
- 即使开放了，也不知道有没有隐患

**做完后用户能看到什么**：
- 数据表详情页有一个「检查 Agent 可用性」按钮
- 点击后展示结果：
  - 通过：绿色
  - 不通过：红色 + 具体原因（"数据集状态为 draft""敏感字段未标记""字段说明覆盖率低"）
- 修复后手动设 `is_agent_accessible = true`

**检查规则**（自动）：
1. 数据集状态为 active
2. sensitivity_level 为 sensitive 或 high_sensitive 的字段都已被标记
3. 字段说明覆盖率 ≥ 50%（`description` 非空的字段数 / 总字段数）

**新增字段**：检查结论需要持久化，否则每次打开详情页都要重新计算。加 1 个字段。

| 新增字段 | 写在哪个表 | 业务含义 | 谁填 |
|---|---|---|---|
| agent_unavailable_reason | datasets（新建） | 最近一次检查不通过的原因清单（JSON） | T6 自动生成，检查通过则清空 |

**已有字段复用**：
- `is_agent_accessible`（已有）——手动开关
- `status`（已有）——检查项之一
- `sensitivity_level`（已有）——检查项之一

**验收**：
- 对字段说明覆盖率低的表点"检查" → 看到阻塞原因
- 补全说明后再检查 → 通过
- 设 `is_agent_accessible = true` → 数据目录中该表显示"Agent 可用"

---

### T7：数据目录列表、字段搜索和统计

**用户现在面临的困境**：
- 「数据目录」页面完全 mock 假数据
- 无法跨表搜索"哪个表里有某字段"

**做完后用户能看到什么**：
- 数据集列表：只展示 active 状态，卡片含名称、来源、业务域、更新时间、Agent 可用、质量状态
- 筛选：来源系统、业务域、Agent 可用
- 搜索：匹配 name / description
- 字段目录：输入字段名（如 `woid`），跨所有数据集搜索，展示所属数据集
- 统计卡片：数据集总数、Agent 可用数

**后端设计要点**：
- 不建独立数据表。数据目录 = datasets JOIN data_sources 的聚合查询
- 字段搜索 = 全文搜索 dataset_fields 的 field_name / field_alias / description

**本任务不需要加新字段**——所有展示数据都来自已有表。

**验收**：
- 打开数据目录 → 看到真实数据集列表
- 字段搜索 `woid` → 找到它在哪个数据集里
- 统计数字与实际一致

---

### T8：数据目录详情页

**用户现在面临的困境**：
- 「数据目录详情」页完全 mock 数据

**做完后用户能看到什么**：

**验收**：打开数据目录详情，所有 Tab 真实数据，敏感字段 Tab 只列 is_sensitive 的字段。

### T11：全链路联调和边界情况

**主流程验证**：
1. 配置 MES 数据源和接入任务 → 执行同步
2. 打开「数据表」→ 看到自动登记的新表
3. 点进详情 → 字段列表完整，主键已标记
4. review 字段、标记敏感字段
5. 打开「数据目录」→ 看到该数据集
6. 字段目录搜索 → 能找到
7. 检查 Agent 可用性 → 设置可用
8. 数据目录中显示"Agent 可用"

**边界情况**：
- 空状态：无同步记录时列表显示空状态引导
- 全量/增量同步：首次登记正常 + 多次不重复
- 同步失败：注册失败不影响同步（数据仍写入物理表）
- 手动删除 Dataset 后再次同步：自动重建
- 物理表增列：增量同步后自动补充新字段
- 并发同步：两个接口同时同步，各自独立

**验收**：以上全部通过。

## 六、依赖关系

```
T1(2个字段) → T2(自动登记) → T3(引擎接入)
                                  ↓
T4(筛选+打标) ←───────────────── T2
  ↑ 不需要新字段

T5(空值率) ←──── T2
  ↑ 加 null_rate

T6(Agent检查) ←──── T4
  ↑ 加 agent_unavailable_reason

T7(目录列表) ←──── T2+T4
  ↑ 不需要新字段
    
T8(目录详情) ←──── T2+T4+T6

T3+T4+T5+T6 → T9(前端数据表)
T7+T8       → T10(前端数据目录)
T9+T10      → T11(联调)
```

**关键路径**（T1 → T2 → T3），只需 3 步就能打通"同步→自动登记"的断点，后续任务可以并行推进。

## 七、实现后的完整工作流

### 数据负责人的日常工作流

```
1. 数据源模块：配置 MES 数据源
2. 接入任务模块：创建接入任务
3. 执行同步 → 自动登记（T2）
4. 数据表列表：看到新表出现
5. 字段列表：扫一眼自动填充结果
6. 标记敏感字段：勾选含隐私数据的字段批量打标（T4）
7. 检查 Agent 可用性 → 设置可用（T6）
```

### 业务用户的数据发现流

```
1. 打开数据目录（T7）
2. 浏览数据集列表，或搜索字段（T7）
3. 点进详情，看字段含义、敏感字段（T8）
4. 确认 Agent 可用 → 去 Agent 查询入口
```

### AI Agent 的数据发现流

```
1. query_objects() → 返回所有 is_agent_accessible=true 的数据集
2. 查具体字段 → 返回字段名、类型、含义
3. 提交查询 → 权限检查 → 执行 → 返回结果 + 来源
```
