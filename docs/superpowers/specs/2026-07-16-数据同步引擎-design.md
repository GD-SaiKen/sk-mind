## 1. 设计背景与约束

### 1.1 平台定位

同步引擎是 AI 原生企业数据平台的**数据接入层核心模块**，位于企业数据源与平台 Raw 层之间。它的职责是把企业内部业务系统（ERP、MES、采购、考勤等）的数据安全、可追踪地接入平台，形成可信数据底座的基础。

### 1.2 第一阶段范围

| 数据库同步 | MongoDB + SQL Server（ERP）只读拉取 | API/HTTP 接口同步（后续阶段） |

### 1.3 实际部署架构与约束

**当前数据源部署情况：**

| 数据源 | 部署位置 | 访问方式 | 可控程度 |
|--------|---------|---------|---------|
| **SQL Server（ERP）** | 生产服务器，不能直连 | 通过中间服务器的脚本当跳板获取数据 | 只读，源端不可修改 |
| **MongoDB（excel-to-db）** | 自主项目，Excel 数据处理后存入 | 直连，完全可控 | 完全自主，怎么高效怎么来 |

**核心约束：**

| 约束 | 说明 |
|------|------|
| ERP 不可直连 | SQL Server 在生产服务器上，平台不直接连接。数据通过中间服务器上的桥接脚本拉取到平台 |
| MongoDB 无限制 | 自主数据库，可直连、可建索引、可建视图，按最高效方式使用 |
| 数据不外泄 | 私有化部署，明细业务数据不离开客户环境 |
| 模块化单体 | 同步引擎作为 FastAPI 后端的一个模块，同步逻辑在 RQ Worker 中异步执行 |

## 2. 总体架构

### 2.1 模块位置

```text
企业数据源（ERP/MES/采购/考勤...）
  │
  ▼
┌──────────────────────────────────────────────┐
│            数据接入层 (Ingestion)               │
│                                               │
│  ┌────────────────────────────────────┐       │
│  │      数据同步引擎 (Sync Engine)      │       │
│  │                                     │       │
│  │  ┌──────────┐   ┌──────────┐       │       │
│  │  │DB Fetcher│                          │       │
│  │  │ MongoDB  │                          │       │
│  │  │ /SQL Server│                         │       │
│  │  └────┬─────┘   └────┬─────┘       │       │
│  │       └──────┬───────┘              │       │
│  │              ▼                      │       │
│  │     ┌──────────────┐                │       │
│  │     │SchemaManager │ ← 建表/比对    │       │
│  │     └──────┬───────┘                │       │
│  │            ▼                        │       │
│  │     ┌──────────────┐                │       │
│  │     │  Validator   │ ← L1拦截/L2打标│       │
│  │     └──────┬───────┘                │       │
│  │            ▼                        │       │
│  │     ┌──────────────┐                │       │
│  │     │  Raw Writer  │ ← 写入raw schema│      │
│  │     └──────────────┘                │       │
│  └────────────────────────────────────┘       │
└──────────────────────────────────────────────┘
  │
  ▼
PostgreSQL ─ raw schema  ─→ clean schema → serving schema
```

### 2.2 核心抽象

| 抽象 | 职责 | 扩展方式 |
|------|------|---------|
| **DataSource** | 管理数据源连接信息与凭据引用 | 新增数据源类型 → 新增连接配置项 |
| **SyncTask** | 统一管理 DB 和 API 同步任务的配置、调度、批次 | 统一模型，不区分源类型 |
| **Fetcher** | 从源端拉取数据，产出统一的行迭代器 | 新增源类型 → 新增 Fetcher 实现 |
| **SchemaManager** | 管理 Raw 表结构（建表、比对、变更检测） | Schema 差异由 DB/API 自动判断 |
| **Validator** | 写入前校验（L1 结构校验 + L2 内容打标） | 规则配置化 |
| **Raw Writer** | 写入 Raw schema 纯物理表，管理批次生命周期 | 统一实现，不区分来源 |

### 2.3 三层关系

```text
DataSource（一个数据源）
  │
  ├── SyncTask #1（同步订单表）
  │     ├── Batch #1
  │     ├── Batch #2
  │     └── ...
  │
  ├── SyncTask #2（同步库存表）
  │     └── ...
  │
  └── SyncTask #3（同步考勤记录）
        └── ...
```

| 概念 | 职责 | 举例 |
|------|------|------|
| **DataSource** | 描述"哪个系统"，管连接信息和凭据 | "ERP 数据库"（host、端口、账号密码） |
| **SyncTask** | 描述"拉什么、怎么拉、落到哪" | "同步订单表——全量、每天凌晨2点、落到 raw.orders" |
| **Batch** | 描述"这一次跑得怎么样" | "7月16日第3次执行，5000行成功，20行拒绝" |

### 3.1 DataSource 核心字段

| 字段 | 类型 | 说明 |
|------|------|------|
| source_id | UUID | 数据源唯一标识 |
| name | string | 数据源名称，如"ERP 数据库" |
| source_category | string | "database" \| "api" |
| source_type | string | 具体类型：mongodb / sqlserver |
| owner | string | 负责人 |
| description | string | 说明 |
| status | string | active / inactive / error |
| connector_config | JSONB | 连接配置（见 3.2） |
| credential_id | UUID | 指向凭据表 |
| connection_status | string | healthy / unhealthy / unknown |
| last_health_check_at | timestamp | 最近一次连接检测时间 |
| created_at / updated_at | timestamp | 审计字段 |

### 3.2 connector_config 配置结构

**MongoDB 类型：**

```json
{
  "db_type": "mongodb",
  "host": "192.168.1.101",
  "port": 27017,
  "database": "business_db",
  "auth_mode": "password"
}
```

**SQL Server 类型（桥接模式，不直连生产库）：**

```json
{
  "db_type": "sqlserver",
  "bridge_mode": true,
  "bridge_url": "http://中间服务器:端口/bridge",
  "database": "erp_db"
}
```

- 平台不直连 SQL Server，通过中间服务器上的桥接脚本获取数据
- `bridge_url` 为桥接脚本的通信地址（可能为 HTTP / 文件目录 / 消息队列，后续确定）
- 具体的 SQL Server 连接凭据由桥接脚本管理，不在平台上配置

### 3.3 连接健康检测

在任务执行前和失败后自动检测连接可用性：

| 检测方式 | 实现 |
|---------|------|
| DB 连接 | MongoDB: pymongo ping；SQL Server: 通过桥接脚本探测 |
| API 连接 | `GET {base_url}` 或指定 health endpoint |
| 凭据状态 | API 返回 401 → 标记凭据可能失效 |

检测结果写入 `connection_status` 字段，在管理台数据源列表页可见。

## 4. 凭据安全模型

### 4.1 Credential 模型

| 字段 | 类型 | 说明 |
|------|------|------|
| credential_id | UUID | 凭据唯一标识 |
| auth_category | string | "database" \| "api" |
| auth_type | string | 具体认证方式 |
| encrypted_value | bytes | AES-256 加密存储的凭据 |
| display_hint | string | 页面展示提示，如"ERP只读账号" |
| expires_at | timestamp | 凭据过期时间 |
| created_by | string | 创建人 |
| created_at / updated_at | timestamp | 审计字段 |

### 4.2 支持的认证方式

| 认证方式 | auth_type | 存储内容 | Fetcher 使用方式 |
|---------|-----------|---------|-----------------|
| 数据库密码 | `db_password` | 加密用户名 + 加密密码 | SQLAlchemy / pymongo 连接字符串 |
| Windows 认证 | `db_windows` | 加密 domain\username + 密码 | SQL Server 连接串加 `trusted_connection=yes` |

### 4.3 安全措施

- 凭据值使用 AES-256 加密后存入 `encrypted_value`
- 加密密钥通过环境变量注入，不写入数据库
- 管理台只展示 `display_hint`，不展示真实凭据值
- 连接 URL、Header 中的凭据信息不在日志中明文输出

## 6. DB Fetcher：数据库拉取策略

### 6.1 职责边界

DB Fetcher 的唯一职责：**从源数据库拉取数据，产出统一的行迭代器**。

- ✅ 连接源库、执行查询、流式读取
- ❌ 不写数据库、不做类型转换、不做业务校验

### 6.2 统一接口

```python
class BaseFetcher:
    def fetch(self, config: SyncConfig) -> tuple[Iterable[dict], FetcherMeta]:
        ...

class FetcherMeta:
    total_rows: int | None
    columns: list[str]
    source_signature: str
    pulled_at: datetime
```

### 6.3 源数据库支持

| 数据库 | 类型 | 连接方式 | 同步模式 | 备注 |
|--------|------|---------|---------|------|
| **MongoDB** | 文档型 | pymongo 直连 | full / timestamp / cursor | 完全自主可控，可建索引/视图，怎么高效怎么来 |
| **SQL Server** | 关系型 | 中间服务器桥接脚本（不直连） | full / timestamp / cursor | ERP 生产库，只读，不建任何对象 |

### 6.4 MongoDB Fetcher 专项设计

MongoDB 是文档型数据库，与关系数据库有本质差异。但得益于我们已有的 API JSON 解析能力（见第 7.4 节），MongoDB Fetcher 和 API Fetcher 可以**复用同一套 JSON → 物理表映射逻辑**。

**MongoDB 到 Raw 表的映射流程：**

```text
MongoDB Collection（集合）
  │
  ▼
pymongo find() → 文档迭代器
  │
  ▼
文档 JSON → JSONFlattener（与 APIResponseParser 共享逻辑）
  │
  ├─ 嵌套对象 → 拍平为列
  ├─ 嵌套数组 → 拆为独立子表
  └─ _id / ObjectId → 转为字符串主键
  │
  ▼
统一的行迭代器 → Validator → Raw Writer
```

**与 SQL Server 的关键区别：**

| 维度 | MongoDB | SQL Server |
|------|---------|-----------|
| 查询方式 | `collection.find({})` + 可选过滤条件 | 桥接脚本执行 SQL |
| 数据结构 | JSON 文档（天然嵌套） | 关系表（扁平行） |
| 列发现 | 采样文档，合并所有字段名（取并集） | 脚本返回的字段列表 |
| 类型推断 | 采样值推断（同 API） | 脚本返回的字段类型直接映射 |
| 嵌套处理 | 必须（JSON 文档天然嵌套） | 不需要（关系表已扁平） |
| 访问方式 | pymongo 直连 | 通过 BridgeAdapter 发指令给中间服务器 |

### 6.5 SQL Server Fetcher 专项设计（桥接模式）

SQL Server 部署在 ERP 生产服务器上，平台**不直连**。数据通过中间服务器上的桥接脚本获取：

```text
平台 (Sync Engine)
  │
  │  ① 发出同步指令（传 SQL / 表名 / 增量标记）
  ▼
中间服务器 (Bridge Script)
  │
  │  ② 连接 SQL Server 执行查询（只读）
  ▼
SQL Server (ERP 生产库)
  │
  │  ③ 返回数据给桥接脚本
  ▼
中间服务器 (Bridge Script)
  │
  │  ④ 将数据返回给平台
  ▼
平台 → Validator → Raw Writer
```

**桥接适配器（BridgeAdapter）**：

由于目前桥接脚本的具体实现方式尚未确定（可能是 HTTP 接口、文件交换、消息队列或其他方式），SQL Server Fetcher 内部通过 `BridgeAdapter` 抽象隔离这一不确定性：

```python
class BridgeAdapter(ABC):
    """与中间服务器桥接脚本通信的抽象接口"""
    
    def execute(self, command: BridgeCommand) -> Iterable[dict]:
        """发送指令给脚本，获取行数据迭代器"""
        ...
    
    def health_check(self) -> bool:
        """检测桥接通道是否可用"""
        ...

class BridgeCommand:
    source_sql: str           # 要执行的 SQL
    sync_mode: str            # full / timestamp / cursor
    last_sync_marker: dict    # 增量标记
```

**后续确定的桥接通道实现**（目前为占位，后续根据实际环境选择）：

| 可能的通道 | 实现思路 |
|-----------|---------|
| HTTP 通道 | 脚本暴露 HTTP 接口，平台发 POST 请求传 SQL，脚本返回 JSON 数据 |
| 文件通道 | 脚本将数据写成 CSV/JSON 到共享目录，平台去读取 |
| 消息队列 | 通过 Redis/RabbitMQ 传递指令和数据 |

**当前状态**：`BridgeAdapter` 先定义接口，使用一个简单的占位实现（如 HTTP 通道），后续根据实际中间服务器环境切换。

SQL Server 端约束：
- 只读查询，不修改任何数据
- 不在 SQL Server 上建视图、触发器、存储过程或任何对象
- 不在 SQL Server 服务器上部署任何程序（桥接脚本在中间服务器上）

### 6.6 三种同步模式

| 模式 | DB Fetcher 行为 | 适用场景 |
|------|----------------|---------|
| **全量（full）** | MongoDB: `collection.find({})`；SQL Server: 桥接脚本执行原 SQL | 小表/集合、首次同步 |
| **时间戳增量（timestamp）** | MongoDB: `find({"updated_at": {"$gt": last_marker}})`；SQL Server: 桥接脚本 SQL 追加 `WHERE updated_at > '{marker}'` | 源端有时间戳字段 |
| **主键游标增量（cursor）** | MongoDB: `find({"_id": {"$gt": last_max_id}})`；SQL Server: 桥接脚本 SQL 追加 `WHERE id > {last_max_id} ORDER BY id` | 源端无时间戳但有自增/单调主键 |

增量同步完成后，记录新的 `last_sync_marker`：
- 时间戳模式：记录本次拉取的 `MAX(timestamp_column)`
- 游标模式：记录本次拉取的 `MAX(cursor_column)`

### 6.7 流式读取

对于大表同步，使用分批方式避免将全表加载到内存：

- **MongoDB**：pymongo 游标分批读取
- **SQL Server**：桥接脚本支持分页/游标，逐批返回数据

```text
源数据库 ── 逐批读取 ──▶ Fetcher ── 逐批 yield ──▶ Validator ──▶ Raw Writer
```

每批默认 1000 行，可根据数据量和内存调整。

## 7. SchemaManager：Raw 表结构管理

### 7.1 职责

SchemaManager 统一管理 Raw schema 下所有同步产出的物理表。**本阶段只处理数据库同步**，建表逻辑聚焦于 MongoDB 和 SQL Server 的字段结构映射。

### 7.2 初次同步：自动建表

**SQL Server（关系型，桥接模式）**：从桥接脚本返回的字段列表获取列定义，直接映射建表。

**MongoDB（文档型）**：采样集合中文档的字段名和值推断类型，嵌套对象拍平为列，嵌套数组拆为独立子表（与 API 同步复用同一套 JSONFlattener 逻辑，详见附录 A）。MongoDB 完全自主可控，可按需建索引加速查询。

```text
Fetcher 产出列信息
  │
  ▼
SchemaManager
  │
  ├─ 检查 raw.{target_table} 是否存在
  │
  └─ 不存在 → CREATE TABLE raw.{target_table} (
        字段1 类型1,
        字段2 类型2,
        ...
        _raw_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
        _source_id UUID NOT NULL,
        _batch_id UUID NOT NULL,
        _pulled_at TIMESTAMP NOT NULL,
        _source_signature TEXT,
        _row_hash TEXT,
        _quality_flags JSONB DEFAULT '[]',
        _ingested_at TIMESTAMP DEFAULT now()
     )
```

### 7.3 后续同步：结构比对

| 场景 | 处理 |
|------|------|
| 结构完全一致 | 无变化，直接进入写入流程 |
| 源端新增字段 | 记录 change_log → 默认**拒绝本次同步**并告警 → 用户确认后 ALTER TABLE 加列，重试 |
| 源端删除字段 | 记录 change_log → 默认**拒绝**并告警 → 用户确认后继续（缺失列填 null） |
| 源端字段类型变化 | 记录 change_log → 默认**拒绝**并告警 → 用户确认后尝试 ALTER，重试 |

### 7.4 Raw 表存储策略

利用 PostgreSQL schema 机制天然分层：

```text
PostgreSQL
├── raw.orders                  ← Raw 层（纯物理表，源端镜像）
├── raw.order_items             ← API 嵌套数组拆分出的子表
├── raw.attendance_records
│
├── clean.orders                ← Clean 层（后续阶段）
├── clean.attendance_records
│
├── serving.order_view          ← Serving 层（后续阶段）
│
└── platform.*                  ← 平台元数据
```

| 策略 | 说明 |
|------|------|
| Schema 分层 | `raw` / `clean` / `serving` 各一个 PostgreSQL schema |
| 表命名 | 用户配置的 target_table 名，无需前缀 |
| 写入模式 | 全量同步 → TRUNCATE + INSERT；增量同步 → INSERT 追加 |
| 索引 | 自动在 `_batch_id`、`_pulled_at`、`_row_hash` 上建索引 |

### 7.5 字段类型映射

**SQL Server 字段类型映射：**

| SQL Server | Raw PostgreSQL |
|-------|---------------|
| nvarchar/varchar/text | text |
| int/bigint/smallint/tinyint | bigint |
| decimal/money/numeric | numeric |
| datetime/datetime2/smalldatetime | timestamp |
| date | date |
| bit | boolean |

**MongoDB 字段类型映射**（与 JSONFlattener 类型推断逻辑一致，详见附录 A）：

| BSON 类型 / JSON 值示例 | Raw PostgreSQL |
|------------------------|---------------|
| String / `"hello"` | text |
| Int32/Int64 / `123` | bigint |
| Double/Decimal128 / `123.45` | numeric |
| Boolean / `true` `false` | boolean |
| Date / ISODate | timestamp |
| ObjectId | text（转为字符串） |
| null | text（警告，取非空文档重新采样） |

## 8. Validator：写入前校验

### 8.1 校验分级

```text
Fetcher 产出的每一行
       │
       ▼
┌──────────────┐
│  L1 结构校验  │  ← 不通过 → REJECT（不进 Raw，记入 error_items）
└──────┬───────┘
       │ 通过
       ▼
┌──────────────┐
│  L2 内容校验  │  ← 不通过 → WARN（进 Raw，但 _quality_flags 打标）
└──────┬───────┘
       │
       ▼
  Raw Writer（带质量标记写入）
```

### 8.2 L1 结构校验（拦截级）

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 字段存在性 | 配置列在源数据中存在 | 拒绝整行 + 记录 error_item |
| 主键/唯一键非空 | `is_unique_key=true` 的字段不能为 null | 拒绝该行 + 记录 |
| 基础类型可解析 | 数值字段不能是 "ABC"，日期字段不能是 "hello" | 拒绝该行 + 记录 |

### 8.3 L2 内容校验（打标级）

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 空值检查 | `required=true` 但值为空 | 写入 Raw + `_quality_flags` 标记 |
| 格式检查 | `format_pattern` 不匹配 | 写入 Raw + 标记 |
| 枚举范围 | 值不在 `allowed_values` 中 | 写入 Raw + 标记 |
| 重复检查 | 唯一键与已有数据冲突 | 写入 Raw + 标记冲突 |

L2 问题不阻止数据进入 Raw 层。后续 Clean 层和用户可以通过 `_quality_flags` 字段看到所有质量问题。

### 8.4 校验规则配置（ColumnRule）

```python
class ColumnRule:
    source_column: str      # 源字段名
    target_column: str      # 目标字段名（可重命名）
    required: bool = False  # L1: 是否必填
    expected_type: str      # L1: string | int | float | date | datetime | bool | auto
    is_unique_key: bool     # L1: 是否作为唯一键
    format_pattern: str     # L2: 正则格式（可选）
    allowed_values: list    # L2: 枚举范围（可选）
```

## 9. Raw Writer：Raw 层写入与批次管理

### 9.1 写入流程

```text
Validator 放行的行（每行带有 _quality_flags）
        │
        ▼
┌─────────────────────────────┐
│  Raw Writer                 │
│                             │
│  1. 每 1000 行为一批          │
│  2. 开启事务                 │
│  3. INSERT INTO raw.{table} │
│  4. 每行自动填充治理字段      │
│  5. 提交事务                 │
│  6. 更新 Batch 统计          │
└─────────────────────────────┘
```

### 9.2 Batch 模型

| 字段 | 类型 | 说明 |
|------|------|------|
| batch_id | UUID | 批次唯一标识 |
| task_id | UUID | 所属 SyncTask |
| trigger_type | string | manual / scheduled / retry |
| status | string | pending → running → success / partial_success / failed |
| started_at | timestamp | 开始时间 |
| ended_at | timestamp | 结束时间 |
| total_rows | int | Fetcher 拉取的总行数 |
| success_rows | int | 成功写入 Raw 的行数 |
| rejected_rows | int | L1 校验拒绝的行数 |
| last_sync_marker | JSONB | 本次同步后生成的新水位标记（成功时回写至 SyncTask.last_sync_marker） |
| error_summary | text | 失败摘要 |
| error_items | JSONB | 拒绝明细列表 |

### 9.3 批次状态机

```text
    ┌──────────┐
    │  pending  │  任务入队，等待 Worker 拉取
    └────┬─────┘
         ▼
    ┌──────────┐
    │  running  │  Worker 正在执行
    └────┬─────┘
         ▼
    ┌──────────────────────────────┐
    │  success      全部成功        │
    │  partial_success  部分成功    │
    │  failed       全部失败        │
    └──────────────────────────────┘

    所有最终状态都可以 → 重试（新建一个 Batch）
```

### 9.4 写入模式

| 同步模式 | Raw Writer 行为 |
|---------|----------------|
| 全量同步 | TRUNCATE raw.{table} → INSERT 全部数据 |
| 增量同步 | INSERT 追加新数据（根据 `_row_hash` 跳过重复行） |

### 9.5 错误项记录（error_items）

每条被 L1 拒绝的记录都需要保存，供用户查看和排查：

```json
{
  "row_index": 15234,
  "source_signature": "erp_db.orders",
  "error_type": "null_primary_key",
  "error_message": "唯一键 order_id 为空",
  "sample_values": {"order_id": null, "customer_name": "XX公司"}
}
```

## 10. 全链路执行流程

### 10.1 同步执行全链路

```text
① 触发（手动 / 定时 cron / 重试）
  │
  ▼
② 创建 Batch（status=pending），投递 RQ 队列
  │
  ▼
③ Worker 拉取 → Batch status=running
  │
  ▼
④ 连接健康检测
  「连接可用？」
    ├─ 否 → batch=failed，告警，结束
    ▼
⑤ 选择 DB Fetcher（MongoDB or SQL Server）
  │
  ▼
⑥ Fetcher.fetch() → 流式行迭代器
  「拉取成功？」
    ├─ 否 → batch=failed，记录错误，结束
    ▼
⑦ SchemaManager 比对 / 建表
  「结构匹配？」
    ├─ 否 → batch=failed，记录 schema_change，通知用户
    ▼
⑧ 逐行：L1 结构校验 → REJECT（记 error_items）
         L2 内容校验 → WARN（打 _quality_flags）
  │
  ▼
⑨ Raw Writer：每 1000 行一批 INSERT
  「写入成功？」
    ├─ 否 → batch=failed，回滚，记录 DB 错误
    ▼
⑩ 更新 Batch 统计
  - success_rows / rejected_rows
  - last_sync_marker（增量模式）
  - batch.status = success | partial_success
  │
  ▼
⑪ 通知（完成 / 失败 / 结构变化告警）
```

### 10.2 调度策略

| 触发方式 | 实现 |
|---------|------|
| 手动执行 | 管理台点击"执行"按钮 |
| 定时执行 | 每个 Task 可配置 cron 表达式，由 APScheduler 触发 |
| 失败重试 | 管理台点击"重试"，新建 Batch |

### 10.3 定时调度

采用 APScheduler（已在技术方案中选用），而不是复杂 DAG 平台：

- 每个 SyncTask 可独立配置 cron 表达式
- 启用/禁用开关，不启动额外调度进程
- 记录每次定时触发的 Batch

## 11. 错误分类与处理策略

| 错误类型 | 表现 | Batch 状态 | 处理策略 |
|---------|------|-----------|---------|
| **连接失败** | 网络不通、密码错误、token过期、主机不可达 | failed | 不自动重试，通知用户排查数据源 |
| **拉取失败** | SQL 执行超时、API 5xx、分页中断 | failed | 保留已有 last_sync_marker；重试从上次位置继续 |
| **结构变化** | 源端新增/删除字段、字段类型变更 | failed | 记录变更详情，通知用户确认，确认后继续 |
| **行级拒绝** | L1 校验不通过 | partial_success | 拒绝行记入 error_items，其余正常写入 |
| **写入失败** | DB 写入事务错误、磁盘满 | failed | 回滚整个批次，通知排查平台数据库 |

### 重试行为

| 场景 | 行为 |
|------|------|
| 全量任务重试 | TRUNCATE 目标表 → 重新全量拉取写入 |
| 增量任务重试 | 使用上次成功的 `last_sync_marker` 继续增量 |
| 部分成功时重试 | 只重试失败的记录（校验失败行或写入失败行） |

## 13. 验收标准

### 13.1 功能验收

| 验收项 | 标准 |

| 凭据安全 | 密码加密存储，页面不展示真实值，日志无明文 |
| 连接检测 | 数据源列表页可见连接健康状态 |
| MongoDB 同步-全量 | 集合文档全量同步，嵌套对象拍平、嵌套数组拆子表 |
| MongoDB 同步-增量 | 时间戳/主键增量同步 |

| SQL Server 同步-主键增量 | 桥接脚本执行主键游标增量 |
| SQL Server 同步-桥接通信 | 平台与中间服务器桥接脚本通信正常 |
| 结构校验 | L1 校验拒绝行记入 error_items |
| 内容打标 | L2 校验问题写入 _quality_flags |
| 批次追踪 | 每次同步生成批次记录，含数据量和状态 |
| Raw 纯物理表 | raw schema 下表为纯物理表，和源端结构对应 |
| 治理字段 | 每行带 _batch_id、_pulled_at、_row_hash、_quality_flags |
| 结构变化检测 | 源端结构变化时拒绝同步并告警 |
| 失败重试 | 失败可重试，增量任务从上次 mark 继续 |
| 通知 | 同步完成/失败/结构变化在平台内通知 |

### 13.2 非功能验收

| 验收项 | 标准 |
|--------|------|
| 大表同步 | 流式读取，10 万行表不 OOM |
| 执行时间 | 全量同步 5 万行以内 < 5 分钟 |
| 行级失败隔离 | 单行 L1 失败不阻塞其余行写入 |
| 日志可追溯 | 每个 Batch 有完整的执行日志 |

### 13.3 暂不验收（后续阶段）

- Excel/CSV/共享盘文件同步
- PostgreSQL、MySQL 数据库同步
- CDC 实时变更捕获
- OAuth2.0 认证
- Oracle 数据库支持
- API/HTTP 接口同步
- 跨任务依赖编排

## 附录A：API/HTTP 接口同步策略（后续阶段）

> 本附录保留 API Fetcher 的设计方向，供后续实现时参考。实际企业 API 的情况很复杂，从已梳理的 MES 等系统 API 文档看，各家接口约定差异很大，不做假设。以下设计思路是一个方向性的框架，后续需要根据实际对接的 API 逐一定制。

### A.1 基本思路

API Fetcher 和 MongoDB Fetcher 共享同一套 JSON → 物理表映射逻辑。核心差异在于数据获取方式——MongoDB 是直连数据库，API 是 HTTP 调用。

### A.2 设计方向

- **HTTP 协议层面**：支持 GET/POST，Content-Type 协商，非标准响应结构
- **分页**：不做假设——实际 API 分页方式各异（page_num、cursor、offset/limit、甚至无分页），需要按接口配置
- **认证**：不做假设——从 MES 实际情况看，有 AccessKey/AccessKeySecret header 认证，也有 Token 认证，需要按接口配置
- **JSON → 物理表映射**：嵌套对象拍平、嵌套数组拆子表，与 MongoDB 共用 JSONFlattener 逻辑

### A.3 后续待确认事项

- 实际需要对接的 API 系统清单
- 各 API 的认证方式、分页方式、响应结构的梳理
- 增量同步策略（API 端是否支持时间范围查询等）
